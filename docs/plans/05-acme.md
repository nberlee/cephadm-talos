# Plan 05: ACME for the RGW serving certificate

Status: signed off 2026-11-03. Scope agreed with the user on 2026-11-03 (decisions at the end).

## Goal

The RGWs behind the ingress VIP serve a certificate from the operator's own ACME server (step-ca, which issues 24 hour certificates), renewed and rolled out without restarts or cut requests, beside today's two sources (a certificate the module generates from its RGW CA, and the operator's own). HTTP-01 validation; TLS-ALPN-01 only if cheap; no DNS-01. Later the other HTTPS endpoints (dashboard, monitoring) take their certificates from the same client once those services exist. The internal mTLS between agents, module and CLI stays on the cluster's agent CA.

## Baseline

Plan 03 as built: an RGW gets its certificate as a base64 PEM bundle in its document, written to `/tmp/rgw.pem` at start (rgw.sh); a new certificate is a new document, rolled host by host with the VIP moved first (step 6e). The leader runs in the agent on the active mgr's host; the agent image is `FROM scratch`, uid 50, restricted, host network. Ceph v21.2.0's beast frontend reads `ssl_certificate=config://<key>` from config-key and, with `ssl_reload=<seconds>`, builds a new TLS context from it periodically; a failed load keeps the previous context and existing connections keep theirs (rgw_asio_frontend.cc, `ssl_reload`, in the v21.2.0 source). Without `ssl_private_key` it reads the key from the same entry. The certificate chains to the ON2IT CA, which the operator adds to the Talos trust store (`TrustedRootsConfig`, `/etc/ssl/certs/ca-certificates.crt` on every node). Ceph keeps config-key out of blanket mon caps (only `allow *` covers it, MonCap.cc), so `client.rgw`'s `mon 'allow rw'` reads no config-key entry today. The new agent code (the ACME client, the responder, admission rules) needs every agent on a new image: through plan 04's agent document updates if it is built first, else through item 11.

## Design

1. **Configuration.** `ceph orch talos acme set --directory <url> --name <vip name> [--name ...] [--contact <mailto>] [--renew-at <fraction>] [--eab-kid <id> -i <hmac file>]`, accepted by the module as a ledger operation (the EAB key, a secret, written at acceptance like an operator's RGW key); `acme status` shows the account, the current certificate, its notAfter, the next renewal and the last error; `acme disable` returns the RGWs to the generated certificate. The names are the ingress VIP's DNS names only; each must resolve to the VIP (checked by the leader before the first order). Defaults: renewal at 2/3 of the issued certificate's actual validity (about every 16 hours for 24 hour certificates, leaving about 8 hours for failures), a check every 5 minutes, retries with backoff capped at 15 minutes. The requested lifetime is the server's (step-ca's provisioner decides; an order may ask for a `notAfter`, which the server may refuse). ARI is not used (`golang.org/x/crypto/acme` has no client for it; scheduling from the actual notAfter does the same job).
2. **Trust.** The ACME client trusts the node's system store and nothing else: the leader's agent reads `/etc/ssl/certs/ca-certificates.crt` through its own machined socket (Talos `Read`, `os:admin`) at each session, so the agent's document gains no mount. No CA of ours is configured.
3. **The client and its state.** The leader runs it in Go (`golang.org/x/crypto/acme`, already a dependency) as a background task of its own, outside the serial ledger, so a renewal that keeps failing never blocks other operations; `acme set` and `acme disable` are ledger operations that only change its configuration and finish at once. Its state is journaled, so a takeover continues it. A renewal cycle: order, validation, finalization, the certificate fetched and published (item 5): done, and the next cycle is scheduled from the new certificate's notAfter, whether or not every RGW has picked it up yet (item 5's convergence check is separate and never delays issuance). A valid order is resumed by fetching its certificate, unless that certificate has less than the publication threshold left, then a new order is made. The task changes no document and no cluster state itself: a document roll (the switch to ACME, `acme disable`, a key rotation) is asked of the module through a bridge call and accepted as a ledger operation, so it runs serialized with every other operation (rolls rely on that: rgw.go `holding` gates revision requests, not other operations); only the ACME requests and the config-key publication run in the background.
   - the account key (ECDSA P-256) is generated and stored as a secret before the registration, bound to the directory URL; a changed directory means a new account;
   - the certificate key (ECDSA P-256) is generated and stored as a secret once per key generation and reused by every renewal's CSR, so a renewal changes only the certificate (item 5); a new key generation (every 30 days by default, or `acme rotate-key`) is the only key change;
   - before an order is created its intent is journaled; the order and authorization URLs are journaled when the server answers. A new leader resumes a known order by its status (pending, ready, processing, valid). An order whose creation outcome is unknown (a crash between the request and the journaled answer) is abandoned and a new one created: at most one duplicate order per crash, which step-ca lets expire;
   - server deadlines are enforced below the library: the client's HTTP transport (a `RoundTripper` around the default) records the `Retry-After` of every response, successful or not, nonce requests and the library's internal polling included, and refuses to send any request before the newest deadline (the call fails, the task resumes later); the task journals that deadline before its next step, so a takeover keeps it. `RetryBackoff` retries only a bad-nonce answer and returns 0 otherwise, so other failures reach the task. The backoff cap never shortens a server's deadline;
   - polling uses the client's own requests (`GetOrder`, `GetAuthorization`) on the task's journaled schedule instead of `WaitOrder`; finalization (`CreateOrderCert`, which polls internally) runs under a 2 minute deadline, and an interrupted finalization is resumed from the order's status (processing or valid, then the certificate fetched from its URL);
   - an invalid authorization or order is terminal: it is abandoned, its tokens removed from the responders, and a new order made after the backoff;
   - new bridge calls, as the bridge releases a fixed set of secrets today (bridge.py:270): `acme account` (read, or store once), `acme key` (store and read an order's key), `acme publish` (item 5), each only for the module's accepted ACME operation.
4. **HTTP-01 responder.** A cluster document of its own on every host of the ingress: a small container from the agent image (`cephadm-talos acme-responder`, the agent image's digest admitted for this document only, as approved), host network, running as uid 0 with `NET_BIND_SERVICE` as its only capability (Talos adds capabilities to the bounding, permitted and effective sets but not as ambient ones, so a non-root process would lose it at exec), a read-only root filesystem, serving `/.well-known/acme-challenge/<token>` on port 80 from a token directory of the records volume (mode 0755, files 0644: key authorizations are public), mounted read-only. The leader writes each token's key authorization through a grant on every ingress host whose agent answers, before it answers the challenge (so a VIP move during validation still finds it), confirms each of those responders serves it (the current VIP holder's at least), answers the challenge, and removes the tokens once the authorization is valid or invalid. An ingress host that does not answer is skipped and gets the current tokens with its next revision when it returns; if the VIP moves to a host without the token meanwhile, that authorization fails and the order is made again (item 3). An interrupted validation is resumed by the authorization's status; a failed one (invalid) ends the order (item 3). The responder is admitted like any cluster document (its image, mount and capability in the admission policy); port 80 must be free on the host (checked before it is granted). TLS-ALPN-01 would need port 443, where the RGW listens: deferred.
5. **Publication and hot reload.** The certificate and its key go into one config-key entry per key generation (`cephadm-talos/tls/rgw/<generation>`, the PEM bundle), which every RGW reads with `ssl_certificate=config://cephadm-talos/tls/rgw/<generation> ssl_reload=300`. RGW reads the entry twice in a reload (the key, then the certificate) and installs the result without checking the pair (rgw_asio_frontend.cc, `ssl_reload`); since a renewal keeps the key, a write between the two reads pairs the same key with either certificate, and both are valid. A new key generation is a new entry and a new reference in every RGW document: the existing roll, host by host with the VIP moved first, about once a month.
   - The leader publishes through the bridge (`acme publish`); the module checks before writing: the leaf for the configured names, server auth usage, the key matching the leaf and the generation's key, at least 4 hours of validity left for a new certificate (the chain to the system store is the leader's check); restoring the latest accepted publication (reconciliation, below) needs only that it is still valid.
   - Ordering: every publication carries a sequence number (the renewal cycle's, journaled by the leader, taken over by successors); the active module writes the entry only if the stored one has a lower number, so a delayed publication of a predecessor cannot replace a newer certificate. The check and the write are not atomic across mgr processes (the bridge's known gap), so the leader also reconciles: each check interval it compares the entry with its last publication and every RGW's served leaf, and publishes again on a difference.
   - Convergence, separate from issuance: every RGW should serve the newest leaf within two reload intervals (a TLS handshake from the leader, as step 6e checks); one that does not (offline, or a failed reload) gets a health warning naming it (`TALOS_ACME_STALE_RGW`) and is checked again each interval, and never holds back the next renewal. During a key rotation's roll, every generation still referenced by an RGW keeps being renewed, and the previous generation's entry and key are retired only once no RGW document references it.
6. **RGW caps.** RGWs read their certificate from config-key, so `client.rgw` gets `allow command "config-key get" with key prefix cephadm-talos/tls/rgw/` added to its mon caps (`allow rw` stays: RGW creates its pools; config-key stays out of it). New RGW identities are created with it; existing ones get it through `auth caps` before their first switch to ACME.
7. **Switching sources.** RGW documents carry either the certificate bytes (generated or the operator's, as today) or the `config://` reference (ACME). The first switch to ACME, and `acme disable`, change every RGW's document once: the existing roll, host by host with the VIP moved first. Admission accepts an RGW document with the `config://` reference only for the module's entries and without certificate bytes; its certificate is then not the agent's to check (item 5's checks take its place). While ACME is on: `daemon add rgw` gives the new RGW the reference (no generated certificate is issued, and the leader's check that the certificate covers the host's names and addresses, rgw.go, is skipped for this source); an ingress placement change keeps the certificate (it names the VIP's DNS names, not addresses; ingress.go's check of the VIP address applies to generated certificates only); `daemon add -i` with an operator's certificate is refused (`acme disable` first).
8. **Bootstrap.** Keepalived depends on its RGW's health, and the VIP must answer for the first validation: the RGWs run with the generated certificate, the VIP comes up, the first order runs and is published, then the switch of item 7.
9. **Expiry and failures.** Renewal is scheduled from the actual notAfter; failures retry until success. A health warning (`TALOS_ACME_RENEWAL`) once the renewal is overdue, an error (`TALOS_ACME_EXPIRING`) under 4 hours of validity left, and `TALOS_ACME_EXPIRED` after notAfter. Every RGW serves the same certificate, so moving the VIP cannot help an expired one: keepalived's check stays a health check (`curl -skf`), and the RGWs keep serving; clients see the expired certificate until the next successful order. When step-ca returns, the next order is published and hot-reloaded without a document change, so the roll and its admission (which refuses an expired certificate in a document) are not involved. `acme disable` is the operator's way back to the generated certificate when step-ca stays down.
11. **Agent update without plan 04.** If plan 05 is built before plan 04's agent document updates, the CLI updates the agents: `cephadm-talos agent update --image <ref>` (operator; the image approved first), applying each host's agent documents (the CLI's own) with the new image, one host at a time, waiting for each agent to answer, the leader's host last after a failover.
10. **Docs.** `docs/architecture.md`: the ACME client in the leader, the responder documents, the bridge calls, the config-key entry and RGW's read of it, the health checks; the capability matrix (`rgw.certificate_source` and related fields); support.md (step-ca tested, the trust store requirement).

## Steps

1. The agent update (item 11, or plan 04's), then the `config://` serving path with the generated certificate (items 5 to 7, publication, ordering, verification, the caps), so hot reload works before ACME exists.
2. The client, its state and the bridge calls (items 1 to 3), against a step-ca on the test cluster's network.
3. The HTTP-01 responder (item 4) and the bootstrap (item 8).
4. Expiry and failures (item 9), docs (item 10).

Each step: a design section here before it is built, a Codex fix-or-refute loop, live checks, docs/architecture.md kept current.

## Tests

- Unit: configuration and its ledger operations; the background task never blocking the ledger; the journaled order state, resumption by status, an unknown order creation; `Retry-After` across a takeover; the module's publication checks and sequence ordering; reconciliation after a delayed old publication; key reuse across renewals and rotation by generation; admission of `config://` RGW documents and the responder; source rules for `daemon add rgw`, ingress changes and `daemon add -i` while ACME is on; health check thresholds.
- Integration (QEMU, with a step-ca issuing 24 hour certificates, its root in `TrustedRootsConfig`): the first issuance and the switch; a renewal hot-reloaded with no failed request under continuous S3 traffic through the VIP; a VIP move during validation; a leader takeover in the middle of an order and in the window of an order's creation; a key rotation's roll; an RGW added and the ingress placement changed while ACME is on; step-ca down across expiry and the recovery after; `acme disable`.

## Out of scope

DNS-01; TLS-ALPN-01 (port 443 is the RGW's); per-host names; ARI; ACME for the internal mTLS; other HTTPS endpoints until their services exist.

## Decisions (user, 2026-11-03)

1. A plan of its own, apart from plan 04.
2. A custom ACME server (step-ca) with configurable lifetime handling; 24 hour certificates are the target.
3. HTTP-01 now; TLS-ALPN-01 if cheap; no DNS-01.
4. The VIP name(s) only.
5. Hot reload, else rolling restarts; v21.2.0's beast reloads from `config://`, so hot reload it is.
6. Trust is the node's Talos system store, to which the operator adds the ON2IT CA; nothing of ours configures CAs.
7. ACME later also for the other HTTPS endpoints; the internal mTLS stays on the agent CA.

## Review

Codex round 6 (2026-11-03), fixed: the 4 hour threshold applies to newly accepted certificates; reconciliation may restore the latest accepted publication while it is still valid, so a delayed old write is undone also near expiry during a CA outage.

Codex round 4 (2026-11-03), fixed: tokens go to every ingress host whose agent answers (the VIP holder's at least); an offline standby is skipped and gets them when it returns, and a VIP move to a host without the token ends in a new order.

Codex round 3 (2026-11-03), fixed: `Retry-After` is captured and enforced in the client's HTTP transport for every response (nonce requests and the library's internal polling included), not only through `RetryBackoff`.

Codex round 2 (2026-11-03), fixed: issuance no longer waits for every RGW (convergence is a separate check with a health warning; every referenced generation keeps being renewed); document rolls go through the serial ledger, only ACME requests and publication run in the background; the library's retries replaced through `RetryBackoff`, finalization bounded and resumed by status; invalid authorizations and orders end in a new order; a resumed certificate too close to expiry is not published.

Codex round 1 (2026-11-03), fixed: the mixed key and certificate read (the key is kept across renewals, rotated by generation through a roll); the RGW caps (an added `config-key get` with a key prefix, `allow rw` kept for pool creation, existing identities migrated); the responder runs as uid 0 with only `NET_BIND_SERVICE` (no ambient capabilities in Talos); publication ordering by sequence number and reconciliation against a delayed old publication; the client as a background task outside the serial ledger with complete renewal cycles; an order's unknown creation outcome; journaled polling deadlines instead of `WaitOrder`; the agent update as a prerequisite (item 11); source rules for RGW additions, ingress changes and operator certificates while ACME is on.

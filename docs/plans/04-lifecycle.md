# Plan 04: lifecycle of hosts, agents and certificates (roadmap milestone 3, part 3)

Status: signed off 2026-11-03. Scope agreed with the user on 2026-11-03 (decisions at the end). ACME for the RGW serving certificate is plan 05.

## Goal

Plan 03 made the cluster changeable through `ceph orch` and left its long-running upkeep to the CLI or to nobody: certificates expire after 3 years and are never revoked, a new node needs the CLI, the agents cannot be upgraded after the handoff, the ledger grows without bound, an uncertain job blocks its node for good, and the leader's identity rests on a heartbeat from its own host. Plan 04 closes those gaps, so a cluster can run for years with the CLI needed only for bootstrap, recovery, approvals and teardown. Two optional modes go further where the Talos cluster allows it: enrollment and repair by the leader (every Ceph node on one Talos CA) and host tracking through Talos cluster discovery. Without them everything works as after plan 03. Milestone 3 is done with this plan.

## Baseline

Plan 03 as built (docs/architecture.md), Ceph v21.2.0, the combined Talos build of PRs #14775, #14781, #14788 and #14795. Every Ceph node is a Talos control plane: Talos containers are not supported on workers (confirmed with the Talos maintainers), so each node's machine config holds the Talos CA key and each agent's machined socket (`os:admin`) can call `GenerateClientConfiguration` (control-plane only, any roles, any positive TTL; it returns the Talos CA certificate with the credential). Talos has no conditional apply: a patch reads the whole machine config, merges and applies it whole (talos.go `Patch`), so two writers can overwrite each other (Known gaps).

## Design

### A. Certificates of the cluster's own CA

1. **Renewal by the module.** The module checks every certificate of the cluster state once a day and renews each that expires within 30 days, as cephadm's certificate manager does. It accepts each renewal as a ledger operation of its own (`renew <kind> <name>`), which authorizes the bridge to release that renewal's new keys and nothing else, so the leader carries it out like any operation and a takeover continues it:
   - mgr certificates: issued by the module (the existing `mgr cert` path), granted as the mgr host's files; the module loads them (item 2);
   - agent certificates: issued by the module, the keys stored as secrets; the leader grants the agent its new document (C2). Depends on C2;
   - generated RGW certificates: issued for at most 1 year from now on (365 days, under the 398 days browsers accept for a server certificate; a setting may lower it), by the CLI and by the module alike (today 2 years in both); renewed 30 days before expiry through the existing reissue and roll of step 6e, triggered by the expiry;
   - the old certificate stays valid until the new one is verified in use (an agent answering with it, the module serving it), then it is revoked (item 3) if it has not expired.
2. **The module reloads its credentials.** Today it reads its server certificate, the CA it trusts and its confirmation signing key only at start; it watches their files and loads them when they change, keeping the old ones on a load that fails.
3. **The operator's client certificate** is the recovery credential. The CLI renews it on any command when it expires within 60 days (reading the agent CA key through exec with `client.admin`, as enrollment does), and the module raises a health warning from 60 days before its expiry, so it is renewed while the mons answer. If it has expired anyway, the CLI's suspension treats an agent refusing the operator certificate for its expiry like an agent that does not answer and suspends that node through Talos (plan 03's item 5).
4. **Revocation.** A certificate revocation list of the agent CA (X.509 CRL; its CRL number only grows), issued by the module whenever a certificate is retired before its expiry (item 1, C5) or on `ceph orch talos revoke <serial>`, and reissued daily with a `nextUpdate` of 7 days. Delivery reaches every verifier, also idle ones: the module sends it with its 30 second status poll to every agent (not only with heartbeats, which go to one agent); successor modules and the CLI read it from config-key at start and per command. Every verifier persists the highest CRL number it saw and refuses an older list, and refuses a peer certificate the list names. Enforcement takes at most one status poll for a reachable agent. An agent whose CRL is past `nextUpdate` (cut off for 7 days) keeps working and reports it (fail open, the default): stale revocation information is an accepted risk; usually a cut-off agent also reaches no mon quorum and gets no confirmation, but that is not guaranteed (status polls and confirmations use separate connections), and a health warning when it returns is enough. For high-security clusters a fail-closed setting: the TLS layer still accepts every certificate of the agent CA, and the agent's handlers refuse every request except the CRL delivery (`POST /v1/crl`, the CRL self-authenticating by the agent CA's signature, accepted also while suspended) and the operator's calls (suspension and recovery); normal access resumes once a newer CRL that is within its `nextUpdate` is installed. The setting is part of the agent's own policy, set by the CLI at bootstrap or by an approval the operator signs, never by the module or the cluster state: the agent keeps it in its records as well as its document, and a document (a restore, a repair, plan 03's resumption rendering it from the state) can only make it stricter; only an approval the operator signs turns it off. The CLI's recovery journal and `local.json` keep the bootstrap choice, so documents the CLI renders carry it. Time comes from the node's clock (Talos's time sync): a tampered NTP server is an accepted risk. The CRL is signed with the agent CA key, which the module holds: it protects against stolen leaf keys, not against a compromised mgr, which can issue certificates anyway (Known gaps).
5. **Rotation of the agent CA and of the operator's approval key** stays in milestone 4 (both need an overlap in which old and new are trusted, built on item 4's delivery).

### B. The leader's identity: an accepted risk, no change

A standby mgr has a CephX key of its own with the same caps and config-key access as the active one and becomes active with one `mgr fail`, so a compromised mgr host, standby or active, is a compromised cluster. Binding confirmations to the active incarnation against a lying standby (ROADMAP milestone 4) defends no real boundary and is not built: the agents get no Ceph identity of their own, and confirmations, heartbeats and the leader-only endpoints stay as plan 03 built them (they fence a stale leader, which is about correctness). With this plan, docs/architecture.md's Known gaps entry on confirmations becomes an accepted risk (every mgr host is trusted as the active mgr is), and ROADMAP milestone 4's items for it (the incarnation evidence, bound confirmations, leader-only endpoints) are dropped, keeping the delivery of revocations (A4).

### C. Hosts and agents

1. **Agent document updates.** The agent's document (its image, certificates, policy inputs) is the CLI's after the handoff. It becomes updatable through the agent itself: the leader grants an agent document, confirmed as any grant, and the agent applies it to its own node only if it passes the agent's own policy, which no grant can change: the image in the operator's approval, the same host identity and agent CA, the same approval key (a new one only when an approval signed with the old one names it), certificates the agent CA issued for that host, and no other field changed. The apply restarts the agent; its apply intent, recorded first, is decided by the next start's reconcile.
   - **Self-upgrade:** the image is pulled on every node first (Talos image pull through each agent); then every non-leader agent, one at a time, each answering on the new image before the next; then the active mgr fails over and the old leader's agent goes last.
   - **Known good:** the state keeps the previous agent image and approval of it; `cephadm-talos agent restore <host>` (operator, CLI) or repair (C4, in the mode) renders the agent's document from the current certificates with that previous image, never an old document whole (it would bring back revoked certificates). The agents' records keep one schema within a release, so a rollback reads them.
2. **Enrollment by the leader (optional mode).** A cluster setting (`mgr/cephadm/talos/leader_enrollment`, off by default), accepted only after the leader proved the condition: every host of the cluster answers with a Talos server certificate of the CA its own node's `GenerateClientConfiguration` returns. With it on, `ceph orch host add <name|addr>` needs no enrollment record:
   - the leader mints a Talos credential through its own machined socket (`os:admin`, 10 minutes, memory only; never in config-key, the journal, the ledger or a log), connects to the target, verifies the target's Talos server certificate against that Talos CA, then reads the node's identity over the connection (hostname, node id, Talos version, CPU flags) and runs the CLI enrollment's checks (version, x86-64-v3, a lowercase hostname, a node without an agent of this cluster);
   - the agent's documents it applies pass the leader agent's own policy (C1's checks, against the leader agent's pinned approval key, agent CA and repositories, an approved image): the cluster state alone cannot change what gets applied;
   - the handoff: the new agent's document carries a one-time enrollment nonce; the leader presents it on `POST /v1/handoff` with its agent client certificate (the leader role), the fresh agent adopts its node (nothing to adopt) at revision 1 and records the nonce as consumed, and the leader removes the nonce from the document with its first revision. An agent whose records are lost later finds no nonce and stays unowned (plan 03's missing-records rule), for the operator.
   - Without the mode, `cephadm-talos host add` enrolls as today.
3. **Remote writes keep plan 03's guarantees.** The leader writes to another node only an agent's own documents, for enrollment (C2), repair (C4) and removal (C5). An agent that stopped may still have an apply of its own in flight (Talos finishes an apply after its caller is gone, and a whole-config apply could undo the leader's), so before writing to a node with an agent of this cluster the leader takes it over the way plan 03's suspension does for an agent that does not answer (item 5, suspend.go): it removes the agent's document if present, waits until every instance is gone, reads the agent's records with a records job, and waits until an apply intent there has settled (`ApplySettle` on that boot); only a fresh node (no agent, no records of this cluster) skips that. Each remote write:
   - is recorded first as a remote intent in the leader agent's records (like a bridge intent: target, documents, time), so a suspension's receipt lists it and the CLI's recovery reserves the target node;
   - is preceded by the leader's check that its incarnation is still active (a fresh `mgr dump` through the bridge, as before every grant), and serialized per target node (one at a time, across incarnations: a successor takes over a predecessor's remote intents from the journal);
   - is sent on a connection of its own, dialled for it and closed after it, with a last-dispatch deadline of one minute after the intent (Talos checks a certificate when a connection is established, not per call, so the credential's expiry alone does not bound an open connection; the deadline is enforced as the CLI's apply deadline is, talos.go), and is decided afterwards by reading the target's config (the documents with the expected hashes); one whose outcome is unknown reserves the target node until `ApplySettle` after its last-dispatch deadline, then is decided from the config, as an agent decides its own uncertain apply.
   - Remote writes run in the leader's tick, so a suspended leader agent sends none, and none goes to a node whose agent's suspension the CLI recorded.
4. **Repair (in the mode).** The leader runs in the active mgr's agent, so a failed leader agent cannot repair itself: the module fails its own mgr over (`mgr fail` of itself) once its local agent has not answered a heartbeat for 2 minutes and a standby is available, so a standby's agent becomes the leader and repairs the old one; without a standby, a health warning and the CLI (`cephadm-talos agent restore`). Repair itself: A host whose agent has not answered for 10 minutes while its node answers through Talos (its agent document missing, crash-looping or stopped) gets its agent documents applied again, rendered from the current certificates and the known-good image if the current one is the one failing, through C3's rules. Re-applying the agent's own documents is not destructive and needs no approval. Never while the cluster is suspended or the host is in maintenance.
5. **Removed hosts.** `host rm` (after its daemons are gone): the leader grants the host's agent its retirement, confirmed as any grant; the agent records it, removes its own documents (agent and records-init; the records volume stays) through its own socket and stops. Once it no longer answers (and, in the mode, its documents are gone from the node's config, read through C3's connection), the module revokes its certificates (A4) and deletes its keys. An agent that does not answer the retirement: in the mode, the leader removes its documents through C3 once it has not answered for 10 minutes; without it, `cephadm-talos host forget <host>` does (the CLI's own documents).
6. **`ceph orch host drain <host>`** and `drain stop`: the drain is a fold state of the host (draining), accepted once; while it lasts the module accepts no new daemon on that host. The leader removes the host's daemons one at a time through the existing removals (RGW with its keepalived first, the mgr after a failover, a mon only while the rest keep quorum, OSDs through their drain), each as its own step journaled under the drain operation, checking between steps whether the drain was stopped. `drain stop` is accepted as a control of the drain (as upgrade controls are, ahead of queued operations): no new step starts, a step in progress finishes. `--zap-osd-devices` is supported (as `osd rm --zap`); `--force` and `--keep-conf-keyring` are refused.

7. **A Talos reboot or shutdown outside the orchestrator (best effort).** noout ownership: the fold keeps, per host, the reasons the module set noout for (maintenance, unplanned stop); the module sets it when the first reason appears and unsets it when the last one goes (maintenance exit included, which today unsets whenever it set it, ledger.go), through the module's existing per-host noout command queue. Ceph's flag has no owner: if the host's noout was already set when the module's first reason appeared, the module records it as the operator's and never unsets it. An operator who sets the flag while a reason of the module holds cannot be told apart from the module's own; `ceph orch talos noout keep <host>` hands it over (the module drops its reasons and never unsets it), and without it the module clears it when its last reason goes (documented). A sequence that aborts without a reboot: if the agent is still up on the same boot 15 minutes after its report, it reports the stop as cancelled and the reason goes. Then: A plain `talosctl reboot`, `shutdown` or `upgrade`, a reboot after a config change or the power button sets no `noout` today, so the host's OSDs are marked out after `mon_osd_down_out_interval` and data moves. The agent watches its own node's `MachineStatus` through its socket; when the stage becomes `rebooting`, `shuttingDown`, `upgrading` or `resetting` (Talos sets it at the start of the sequence, before it stops containers), the agent tells the module over its existing channel to the module (`POST /v1/going-down`, its agent client certificate), and the module runs `osd set-group noout` for the host's CRUSH bucket (the command maintenance uses, refused for the same host names) and records an unplanned stop of that host in the fold, apart from a maintenance. After the boot the agent reports its new boot id; once the host's OSDs are up again, the module clears the noout, only one it set itself and only if no maintenance or operator set it meanwhile. The stage changes before Talos stops containers, so the message normally goes out first; the agent sends it at once and retries for its stop timeout. The daemons do not depend on the agent (that would keep them from starting while the agent is down). Limits: it only notifies (no ok-to-stop, the reboot is Talos's); a power loss, panic or hard reset gives no signal (Ceph's down-out interval applies); two hosts going down at once can still lose mon quorum; a host that never comes back keeps its noout until the operator clears it or removes the host (a health warning after 30 minutes).

### D. The ledger and journal

1. **Ledger compaction and its size.** The module folds finished operations into a snapshot (the fold and the takeover cutoffs at a sequence number), chunked against the config-key entry limit as the cluster state's records are, published under its sequence number before the folded entries are deleted; a reader takes the newest complete snapshot and the entries after it. The module reads the ledger by key (list, then get) instead of one dump, so its size no longer has the 256 KiB limit, and it accepts no new operation while more than 500 are unfinished (backpressure, with the reason). The request-uuid lookup of `orch talos request` keeps its window over the snapshot.
2. **Journal pruning.** The leader deletes a finished operation's journal records once the published state's `ledger_applied` is past it, and a takeover's journal import skips every operation whose ledger entry is at or below the newest snapshot's sequence number (finished by definition), so a predecessor's older record of a pruned operation is never brought back.
3. **Resolving an uncertain job.** `cephadm-talos resolve <host> <operation>` (operator certificate, `POST /v1/resolve` on that agent): the agent marks the job failed and runs jobs again, but only once it is sure the job cannot still run: no document and no instance left, no apply intent open (the same conditions as its reconcile). Only failed: a done preparation needs its result (the OSD id and uuid), which the operator cannot supply safely, so the creation fails and the operator cleans up (`ceph osd purge-new`) and adds the OSD again.

### E. Talos cluster discovery (optional mode)

The leader's agent reads the Talos `Member` resources of its cluster from its own socket (`os:reader`): node id, hostname, machine type, Talos version and addresses. On when discovery is enabled on the nodes (it works without Kubernetes); without it, hosts are tracked as today. Discovery is a hint: a node is the cluster's host only after it was authenticated (C2, or the CLI's enrollment), and members expire only after discovery's 30 minute TTL, so a departure warning complements the agents' heartbeats (stale after 2 minutes) and never replaces them.

1. **Identity.** Enrollment records each host's node id. Changes are classified and reported as health warnings, with what follows:
   - **gone**: a host's node id leaves with no successor: `TALOS_HOST_GONE`, always;
   - **rename**: the same node id under another hostname: `TALOS_HOST_RENAMED`; the host keeps its Ceph name (daemon ids, certificates). Admission checks a generated RGW certificate against the host name in the agent's own identity (its certificate, the Ceph name), not the node's current Talos hostname (node.go, admit.go), so RGW and keepalived revisions of a renamed host keep passing;
   - **address change**: a known node id with a new address. First the trust: the leader and the module verify agents and mgrs by their certificate's identity (URI SAN), not by IP SAN hostname verification as the leader does today (leader.go), so a moved host stays reachable before its certificates are reissued. Admission no longer re-checks a retained, unchanged document against node facts that changed since it was admitted (its address, its hostname): it was admitted before and only the node changed; a changed document is checked in full. So the roll that follows a move (keepalived removed first, then the RGW's revision with the new address and a certificate naming it) passes with the RGW still rendered for the old address, also after the old address is gone; the RGW's certificate is reissued and rolled before the mon moves. Then `ceph orch host set-addr <host> <addr>` (implemented, accepted from the operator, or from the leader's report in the leader-enrollment mode) updates the host's address in the fold and the state, and the leader follows, one host at a time while the other mons keep quorum: first the generated RGW certificate naming the new address and keepalived's unicast peers (the roll above), then the mon leaves the monmap and is added again under its name at the new address, then `mon_host` in every `ceph.conf` and the agent's and the mgr's certificates with their IP SANs (A1). Several mons at once (a renumbering) or without quorum: reported, never attempted.
   - **replacement**: a new node id with the hostname and address of a host that left (a reinstall wipes the node identity, new hardware has its own): `TALOS_HOST_REPLACED`, naming the successor. Identity is read from the affiliates (one per node id), not the members, which Talos builds by node name (member.go), so two machines with one hostname show as two affiliates. Discovery is no fencing: an affiliate that expired may be a partitioned machine still running its daemons. `ceph orch talos replace <host> --old-node-is-gone` (operator only, never automatic, the operator's statement that the old machine is wiped or off) runs a protocol of its own, since the successor has none of the predecessor's records: the old host's agent certificates are revoked and its sessions closed; its operations whose outcome is unknown are failed (their node is gone) and its reservations released; the host leaves maintenance in the fold if it was in it; then the successor is enrolled under the same name as a new generation of the host (C2 in the mode, `cephadm-talos host add --replace` without), and its daemons are deployed again: OSDs whose disks carry this cluster's BlueStore label with the OSD's uuid from the state are activated from the label, its mon is added again (a fresh store that syncs), its mgr and RGW deployed again.
2. **Enrollment by name.** In the leader-enrollment mode, `ceph orch host add <hostname>` takes the address from the members.
3. **Auto adoption (opt-in).** `mgr/cephadm/talos/auto_adopt`, for clusters where Ceph runs on every node: every new control-plane member is enrolled as with `host add` (a replacement is not: it waits for the operator, E1); reported by the leader to the module, which accepts the operation itself. Needs the leader-enrollment mode.
4. **Recovery.** The CLI's contacts come from the members when `local.json` is gone: `--node <addr>` with any talosconfig of the cluster finds the rest.

## Step 1 design: the module's credentials, the operator's certificate, renewal of mgr and RGW certificates (2026-11-03)

1. **The module reloads its server credentials (A2).** The 5 second leadership loop (module.py `_lead`) compares the content of `agent-ca.crt`, `mgr-server.crt` and `mgr-server.key` with what the channel loaded. On a change it reads the three files once, builds a new server context (`server_context`) and the signing key from those same bytes and, only if the certificate and key load and match, replaces one credentials object (context, signing key, CA) that both servers hold (4722, 4723); a load that fails keeps the old one and logs it. Each connection captures the credentials object when it is accepted and signs its confirmations with that object's key, so the key always matches the certificate the agent saw in that handshake (channel.go `verifyConfirmation` checks against it), also while a swap happens. The client certificate is already read per request.
2. **Renewal operations.** Two new ledger kinds the module accepts itself, without a `ceph orch` command: `renew_mgr` (host and daemon `mgr.<host>`, through `_accept` with its busy check but not the maintenance check: a mgr whose certificate expires during maintenance is renewed in the state only: no revision is granted to a host in maintenance (its mgr files are removed, and the host may be off), the renewal goes straight to `mgr cert done`, and the exit renders the new certificate, which admission accepts) and `renew_rgw_cert` (hostless, through `_accept_cluster`, refused while another `renew_rgw_cert`, an ingress apply or an RGW add is unfinished). The module's leadership loop checks once a day (and at its first tick) the certificates in use, read from the published state's host, daemon and RGW records (`record_from_store`, not the inventory's single expiry): each mgr's server and client certificate, and the generated RGW certificates in use: the ones current RGW daemons reference (not the retired ones `RGW.Certs` keeps) and the one each RGW actually serves (a TLS handshake from the module to the RGW, reading the leaf), since a roll updates the state before the revision lands (rgw.go) and a failed roll can leave an RGW on the old certificate the state no longer names. It accepts a renewal for each that expires within 30 days, unless an unfinished one exists for it. A renewal refused (its host busy with another operation, such as the host's other renewal, an OSD add or a suspension) and a check that fails are tried again by a check 10 minutes later, not the next day's: with many hosts, refusals are common and a day's wait per refusal would leave renewals behind (found live: a host's mgr and agent renewals refused each other). A host's due renewals are accepted the earliest expiry first, so the most urgent one is not the one refused.
3. **`renew_mgr` in the leader.** It calls `mgr cert` with the renewal's id. The bridge's `_mgr_cert` also accepts an executable `renew_mgr` whose mgr is in the fold's open generation: the same identity, the host's address and name from the fold, new keys under `issued/<op>/<attempt>/`; issued once per operation (a repeated call returns the earlier attempt, as `_rgw_cert` does), so a retry or a takeover reuses it. The leader journals the certificates it had before, records the new ones and `MgrKeys` in the state and grants the host's revision (the mgr files, `render.MgrFiles`). It then waits until the module on that host serves the new server certificate, if it is the active one (a TLS handshake to 4722; a standby loads its files when it starts), and asks `mgr cert done` (a module entry `mgr_cert_done {of, keep}` that deletes the keys of that mgr's other certificates). A renewal that ends failed before the leader journaled that it asks `mgr cert done` restores the journaled certificates in the state (their keys still exist), so the daily check sees the installed certificate again and renews anew; once that step is journaled, the new certificates stay and a retry or a successor repeats `mgr cert done` (idempotent) until it is answered. The fold's release rule (ledger.py `secret_allowed`, bridge `secret get`), derived from the ledger alone: for a mgr's open generation, the keys of its add and of every `renew_mgr` after it that no later `mgr_cert_done` retired.
4. **Admission of retained documents.** A roll's first revision removes keepalived and keeps the RGW's document as it is, and admission today checks the retained RGW's certificate again (admit.go `rgwCerts`), refusing one that expired, so an RGW whose certificate expired could never reach its replacement. A retained document unchanged from what the agent owns is not checked again against facts that changed since it was admitted (its certificate's validity, the node's address and hostname); a changed document is checked in full. Plan 04's address change (E1) relies on the same rule.
5. **`renew_rgw_cert` in the leader.** For generated certificates only: `rgw cert` (the bridge's `_rgw_cert` also accepts an executable `renew_rgw_cert`, once per operation as today) for every RGW host and the VIP as today, recorded in `st.RGW.Certs`, rolled with `rollRGW`, then `rgw cert done`, as an ingress change does (ingress.go `ingressCert`). A roll a predecessor left half-done is finished with its certificate only while that certificate is valid for longer than the renewal threshold; otherwise the renewal supersedes it, rolling every RGW (also those already on the unfinished roll's certificate) to the new one, and `rgw cert done` keeps only the new one. A host's VIP-off step grants only the removal of its keepalived document, not a re-rendered revision: a grant replaces or removes only the documents it names (node.go `Apply`), so the RGW document stays exactly as the agent owns it, whatever the state names after a failed roll, and admission checks it as retained and unchanged (item 4); only the RGW's own revision after it installs the new certificate. The daily check reads which certificate each RGW daemon references, so an RGW still on the old one after a failed roll keeps it due. An RGW host in maintenance is not visited by the roll (today `rollRGW` visits every RGW and waits for each to serve, rgw.go): its RGW's reference is set to the new certificate in the state, so the exit renders it, and the roll goes on with the running RGWs. An operator's certificate is not renewed: a health warning names it from 30 days before its expiry.
6. **1 year.** Generated RGW certificates are issued for 365 days: the module's `issue_rgw_cert` and the CLI's `newServerCert` (pki `Lifetime`).
7. **The operator's certificate (A3).** The CLI renews it on any command, also after the handoff, when it expires within 60 days: it reads the agent CA key through exec (the secrets, as enrollment does), issues the certificate, saves `local.json`, and on every command (renewed or not, also at the handoff) makes the public copy in config-key, `cephadm-talos/operator.crt`, equal to its certificate, so a copy a failed write left behind is corrected by the next command. The module reads that entry in its daily check and raises `TALOS_OPERATOR_CERT_EXPIRING` from 60 days before. If the CLI's certificate has expired when it suspends, it skips the agent calls (they would be refused) and suspends every node through Talos (plan 03 item 5's path), which needs no operator certificate. It never interprets a TLS error as expiry: it checks its own certificate's notAfter.
8. **Health checks.** The module sets its health checks (`set_health_checks`, a first): `TALOS_OPERATOR_CERT_EXPIRING`, `TALOS_RGW_CERT_EXPIRING` (an operator's RGW certificate within 30 days), and `TALOS_CERT_RENEWAL` (a certificate within 7 days of its expiry, so its renewal keeps failing).
9. **Docs.** docs/architecture.md: the identities table's lifetimes and renewal, the admission rule for retained documents, the module's reload, the new ledger kinds and module entries, the release rule, the health checks, the operator certificate in config-key; the Known gaps entry "no renewal after the handoff" narrows to agent certificates (step 2).

## Step 2 design: agent document updates, self-upgrade, renewal of agent certificates (2026-11-03)

1. **A self-update grant.** A new grant kind carries only the variable fields of the agent's own documents: its image and its certificates with their keys. The agent renders the agent and records-init documents itself (`daemons.Agent`, `daemons.RecordsInit`) from those fields and its own pinned inputs (CA, repositories, approval key: what its current document has, so no copy rendered elsewhere has to match), and applies them after its usual confirmation, only if:
   - the image is the one it runs, or by digest, in the operator's approval and from the repository of its current image (the agent image is not in the cluster's repositories, admit.go `image`); the handoff's first approval names the agent image from now on;
   - the certificates are issued by its agent CA for its own identity (`agent/<host>`), the server certificate covering the host's address and name, each matching the key the grant carries;
   - it is not suspended (plan 03 slice D refuses every grant then).
   The node keeps excluding these documents from its cluster documents and ownership (node.go `handoff`), so drift and the readoption are unaffected. Pinned inputs never change through a grant (their rotation is milestone 4).
2. **Its outcome.** A self-update uses the apply intent every apply uses (node.go `applyIntent`, with the before and sent hashes of the agent's documents and a mark that it is a self-update), so an undecided one blocks every later apply, cluster grants included (Talos patches the whole machine config, so a delayed self-update could undo a later grant), and suspension's receipts, the records job and the resumption see it as they see any apply intent. After the patch, and on a later start if the patching process was killed (Talos replaces the agent's instance once the new image and the new records-init's success are there), the agent decides it from the node's config as an apply's (sent: completed; before after `ApplySettle` or on another boot: refused; else uncertain), writes a self-update record (the operation, the hashes applied) before it removes the intent, and the operation record follows that record.
3. **Agent certificates from the module (A1).** A bridge call `agent cert` issues a host's agent server and client certificates (3 years, as the CLI does) once per operation, with a module entry `agent_cert {of, attempt}`, the keys as secrets `issued/<op>/<attempt>/agent-{server,client}.key` (the certificates beside them). The state records `AgentCert`, `AgentClientCert` and `AgentKeys` ("<op>/<attempt>", empty for the CLI's `host/<host>/agent-*.key`), as `MgrKeys` does. The bridge releases a host's agent keys only to the leader carrying out that host's agent operation. The CLI's recovery finds them through the state's `AgentKeys`; when the suspension removes an agent it journals, besides its certificates, its pinned inputs (repositories, approval key) and the secret names of its keys, and `agentHost` takes the state first, then that journal, then an enrollment record. A host the leader removed keeps its agent keys until plan 04's C5 retires them. `agent cert done` (a module entry `agent_cert_done`, then the host's other agent keys deleted) follows the rule of `mgr cert done`: only what the fold retired.
4. **`renew_agent`.** The module's daily check also covers every host's agent certificates (renewed within 30 days or the test setting). The leader: `agent cert`; journals the host's previous certificates; records the new ones in the state; grants the self-update with the agent's current image; waits until the agent answers with the new server certificate (a TLS handshake to 4721); journals the retirement and asks `agent cert done` until answered. A renewal that ends failed before the retirement is journaled restores the previous certificates in the state. A host in maintenance is renewed like any other (the agent keeps running in maintenance). The leader's own agent restarts with its renewal and continues the operation from the journal.
5. **`ceph orch talos agent upgrade --image <ref>`** (a module command, refused unless the image is by digest, in the operator's approval and from the agent image's repository, and no other agent upgrade or Ceph upgrade runs), accepted as the hostless kind `upgrade_agent {image}`; the operation finishes once the leader recorded the upgrade, whose steps then run between ledger operations, one at a time, as the Ceph upgrade's do (a paused agent upgrade blocks nothing else; `--resume` is a control that changes only the record). Its progress is a record in the cluster state (`AgentUpgrade`: the operation, the image it upgrades from, the target, the hosts done, the host left for last, paused or not), recorded before its first step, so a successor or the leader's own restarted agent continues from the published state as the Ceph upgrade's record allows today. The leader:
   - has every agent pull the image on its own node through a confirmed pull grant (the agent checks the digest against the operator's approval and its image repository, and refuses while suspended), and waits until each has it;
   - grants every non-leader agent its self-update with the new image, one host at a time, each answering on the new image (its node report's running digest of the agent's container) before the next; an agent that does not come back within 10 minutes pauses the upgrade (`ceph orch talos agent upgrade --resume` after the operator's restore);
   - then, if a standby mgr is available, fails the active mgr over so a successor continues and upgrades the old leader's agent; without a standby, the leader's agent upgrades itself last and continues from the record after its restart;
   - at the end records the target as `Agent.Image` and the image it upgraded from as `Agent.PreviousImage` (the known good).
6. **`cephadm-talos agent restore <host> [--previous]`** (operator, CLI): part of a recovery session, as the CLI writes to a node only while its agent is suspended (plan 03 slice D's suspension, including an agent that does not answer: its removal, its instances gone, its apply intent settled). It applies the host's agent documents (the CLI's own) rendered from the state's certificates (keys through `AgentKeys`), the pinned inputs journaled at the suspension or read from the node's current agent document, and the current image, or with `--previous` the known good: an unfinished agent upgrade's from-image, else `Agent.PreviousImage`; never an old document whole. An interrupted self-update can leave an apply intent whose before and sent renderings both differ from the restored one, which would block the readoption for good: once the restored documents are in the node's config, the restore settles such an intent through the records job (plan 03 slice D's, run as uid 50 with the records volume): it records the self-update's operation as failed (superseded by the restore) and removes the intent. Only an intent marked as a self-update is settled so, never a cluster apply's. The restored agent starts suspended from its records; `cephadm-talos resume` ends the session as usual. Restore checks that the agent then runs the intended image and certificate, not only that it answers.
7. **`ceph orch talos agent upgrade --stop`** (added after the live check, user 2026-11-03: a paused upgrade to an image that does not start could only be resumed into the same failure, and while unfinished it refuses every other agent or Ceph upgrade). Accepted as the hostless kind `upgrade_agent_stop {upgrade}` while an agent upgrade is unfinished and is not already stopping, and only if the image it upgrades from is in the operator's current approval (the agents check it again); like `--resume`, a control that changes only the record and runs ahead of queued operations; a step in progress first ends (its agent answers, or it pauses at its 10 minute limit). The leader turns the upgrade into a rollback in its record: `stopped` (the target it gave up), the target becomes the image it upgraded from (`from` itself stays, so `agent restore --previous` keeps meaning that image), a new attempt, not paused, the pulled hosts cleared (the old image is pulled again through pull grants: nothing guarantees a node kept it) and the hosts done those whose agent runs the old image's digest (their node report). The steps then continue as an upgrade's, with the same rules: self-updates one host at a time, the leader's own host last (a failover with a standby), done hosts checked again before the end, a step that does not end within 10 minutes pauses it. An agent that does not run (the target's image does not start) cannot update itself: its step pauses, the operator restores it (`agent restore --previous`, the old image) and resumes the rollback with `--resume`, which then finds it done. At the end `Agent.Image` and `Agent.PreviousImage` are unchanged and the record is finished, marked stopped; a new upgrade may start. `--stop` of a rollback is refused; the module shows a stopped upgrade as stopped.
8. **Docs.** docs/architecture.md: the self-update grant and its checks, the pull grant, the agent certificate calls and release rule, the new ledger kinds, agent restore, the stop; the Known gaps entry on agent renewal goes.

Codex round 1 of this design (2026-11-03), fixed: a self-update uses the common apply intent (blocks cluster applies until decided, seen by suspension and recovery) and writes a durable record before removing it; the agent renders its documents from its own pinned inputs and the grant's variable fields; the running image needs no approval for a certificate-only update, the handoff's approval names the agent image; restore runs inside a suspension and uses the journaled or current pinned inputs; `--previous` takes an unfinished upgrade's from-image; the upgrade's progress is a record in the cluster state; pulls are confirmed grants checked by the agent; recovery journals the removed agent's key names and pinned inputs.

Codex round 2 of this design (2026-11-03), fixed: a restore settles an interrupted self-update's intent through the records job (only a self-update's), so the readoption is not blocked.

Live check: an agent certificate renewed by the module on every host, the leader's included, without a lost grant; an agent upgrade to a new build across all hosts with a failover, a bad image (one that does not start) paused and restored with `agent restore --previous`.

## Step 3 design: the agent CA's revocation list and its delivery (2026-11-03)

Verifiers of agent CA certificates today (all TLS 1.3, identity by the URI SAN): the agent's server on 4721 (agent.go `TLSConfig`, any mgr, agent or operator of the fsid, each handler checking the role); the module's servers on 4722 and 4723 (bridge.py `load_credentials`, `peer()`); the Go clients (agent to module confirmations, channel.go; leader to bridge, bridge.go; leader to agents, leader.go `agentClient`; the CLI's operator clients, suspend.go, handoff.go, restore.go); the module's clients (status poll `fetch_record`, heartbeat `post_json`); admission of mgr files and self-update certificates (admit.go `mgrCert`, selfupdate.go `selfCert`). Handshake-only probes (`servesCert`, `served_leaf`) authenticate nothing and stay as they are. The RGW CA is not part of this.

1. **The revoked set: one config-key entry per revocation.** Revocations are kept apart from the ledger, so no takeover's cutoff (ledger.py excludes a predecessor's entries after its snapshot) can drop one: each is a config-key entry `cephadm-talos/revoked/<serial>` (`{not_after, reason}`), outside `mgr/`, written before any certificate or key it concerns is deleted and never changed afterwards. Writing one is idempotent and only adds; a stale module writing one revokes what it retired anyway, and none is written for a certificate in use (the kept ones are never listed). The revoked set is every such entry whose `not_after` has not passed (plus one day); the active module deletes older ones, so the set does not grow forever. The writers:
   - the bridge's `mgr cert done`, `agent cert done` and `retire` (daemon removal) write the entries of the certificates they retire, then their module entry as today, then delete keys; a retried call writes them again (idempotent) and deletes what the fold retired. The certificates' sources: every issuance attempt keeps its certificates beside its keys (`issued/<op>/<attempt>/*.crt`; the mgr add path stores only keys today and stores both from now on), read before the keys are deleted; the CLI's or an earlier renewal's: the previous certificates the leader journaled and passes with the call, each checked by the bridge (issued by the agent CA, for that host's identity and role, not the kept ones); a mgr's removal: the leader journals the mgr's certificates before it clears them from the state, and `retire` carries them;
   - `ceph orch talos revoke <serial> [--until <date>]` (a Write command, for the operator; without `--until` it is kept for 3 years, the longest lifetime we issue);
   - the operator certificate: the CLI's renewal after the handoff writes the old serial and expiry as pending in `local.json` together with the new certificate, before it publishes the new one, and runs `ceph orch talos revoke` (through exec with `client.admin`) on every later command until it succeeded, then clears it. Before the handoff nothing is revoked (no list exists yet; the CLI's renewals then replace certificates of a cluster not yet in use);
   - host removal (C5, step 6) writes the same entries.
2. **The list.** The active module issues an X.509 CRL of the agent CA (cryptography's `CertificateRevocationListBuilder`, signed with `agent-ca.key` from the secrets, authority key identifier as in daf08be) whenever the revoked set differs from its last list's and at least daily, with `thisUpdate` now and `nextUpdate` 7 days later (module option `talos_crl_valid_minutes`, 5 to 10080, only to shorten it for tests; a shortened list is reissued at half its validity). Its CRL number is the leadership's mgr map epoch times 2^32 plus a counter of the lists issued in that leadership, so a delayed predecessor's list always has a lower number than any of its successor's, and verifiers keep only the highest. It is published in config-key outside `mgr/` like the ledger, in chunks with a manifest as the cluster state records are (`cephadm-talos/crl/<number>/<i>` and `cephadm-talos/crl/manifest` with the number, the chunks and their sha256), since a config-key entry is limited to 64 KiB; older numbers' chunks are deleted after the manifest moved on. A module that reads a manifest with a lower number than its own last list publishes its list again, so a predecessor's late write does not hide the successor's. Issuance runs in the leadership loop's thread once the leadership is confirmed, before and independent of the heartbeat (a fail-closed agent may refuse heartbeats until it has a new list).
3. **Agents.** The status record (`GET /status`) reports the agent's CRL number and whether its list is past `nextUpdate`. Delivery is apart from the poll's authentication: in its 30 second poll the module sends `POST /v1/crl` (the DER list) to every inventory host whose poll failed or reported a lower number, with its mgr client certificate, verifying the agent's server certificate against the agent CA but not against the revoked set (the list is public and authenticates itself, so a revoked or impostor server learns nothing; an agent whose own server certificate was revoked still gets lists). The agent accepts a list only if it is signed by its agent CA, names that CA as issuer, has a CRL number higher than the one it holds, a `thisUpdate` not more than 5 minutes in the future and a validity (`nextUpdate` minus `thisUpdate`) of at most 7 days, the limit fixed in the agent, not set by the module; it writes it to its records (`crl`, atomically) before it installs it (an atomic pointer), and on start installs the list from its records. `POST /v1/crl` is accepted from any certificate of the agent CA that is not itself revoked, also while suspended. Every Go verifier checks the peer's serial against the installed list: the server on every request (a middleware over all handlers, since a kept-alive connection outlives its handshake; it also checks the peer certificate's expiry, so pruning an expired revocation re-admits nothing), the client callbacks of the leader and the agent, admission's `mgrCert` and `selfCert`. A self-update or a restored document starts the agent with its records, so the list survives its restarts.
4. **The module's verifiers.** The module is the list's issuer: its servers (`peer()` on 4722 and 4723, on every request, also checking the peer certificate's expiry) and its clients (poll, heartbeat) refuse a peer whose certificate's serial is in the revoked set, read from config-key with the ledger each tick (no CRL parsing, no OpenSSL CRL flags, whose expiry check would fail closed).
5. **The CLI.** Before each command that connects to an agent, the CLI reads the published list (through exec, as the state), checks it as an agent does and keeps the highest one it saw in its cluster directory (`crl.der`), which it uses when the mons do not answer (suspension, recovery); its clients refuse an agent whose server certificate the list names. The operator certificate is never refused by the CLI itself; agents refuse a revoked one.
6. **Staleness: fail open by default.** An agent whose list is past `nextUpdate` keeps working and reports it; the module raises `TALOS_CRL_STALE` naming those agents (the warning when a cut-off agent returns), and `TALOS_CRL` when it cannot issue or publish a list. The module itself never goes stale (it is the issuer).
7. **Fail closed, for high-security clusters.** The setting is the agent's own policy, never the module's or the cluster state's:
   - `cephadm-talos bootstrap --crl-fail-closed` sets it: an environment variable of the agent's document, a pinned input (the self-update keeps it from the current document, as the CA and repositories), kept in `local.json` and the recovery journal so documents the CLI renders carry it;
   - the agent also keeps it in its records (`crl-policy`, with the approval serial that last set it). Precedence: a setting signed by the operator (the record holds one) wins over the document's in both directions, also after a restart; without one, the document's applies and a document can only make the recorded setting stricter (a restore or repair cannot weaken it);
   - `cephadm-talos crl-policy closed|open` changes it later: the CLI signs an approval with the operator's approval key carrying a new field `crl` (`closed` or `open`) and sends it to every agent with the operator certificate (`POST /v1/policy`, as suspension's calls are sent); the agent verifies the signature, the fsid and that its serial is higher than the one its `crl-policy` record holds, then records it; the CLI also writes the new setting to `local.json` and the recovery journal, so documents it renders afterwards agree. The field never comes through a grant or the module.
   With it set and the list past `nextUpdate` (or no list once the first was due after the handoff), every handler refuses with 503 except `POST /v1/crl`, `POST /v1/policy`, `GET /status` (so the module sees why) and the operator's calls (suspension, re-adoption, activation, handoff); normal access returns once a list within its validity is installed.
8. **Docs.** docs/architecture.md: the revoked set and its entries, the list and its delivery, every verifier's check, staleness and the fail-closed setting; the Known gaps entry on revocation goes.

Codex round 1 of this design (2026-11-03), fixed: the CRL number from the leadership's mgr map epoch and republication over a predecessor's late write; revocation checked on every request, not only at the handshake; every issuance attempt keeps its certificates, a removed mgr's are journaled before the state drops them; the operator certificate's pending revocation in `local.json`, retried until accepted; delivery apart from the poll's authentication, so an agent with a revoked server certificate still gets lists; `POST /v1/policy` with an operator-signed approval, accepted by a stale agent, turns fail closed on and off; issuance independent of the heartbeat; the agent caps a list's validity at 7 days, the module option only shortens it; chunked publication.

## Step 4 design: ledger compaction, journal pruning, resolving an uncertain job (2026-11-04)

Today (inventory): the module reads the ledger once per incarnation with one `config-key dump` of `cephadm-talos/ledger/` (ledger.py `Ledger.open`), which fails past the 256 KiB output limit (bridge.py `MAX_OUTPUT`), and then `_authority` refuses everything; nothing is ever deleted. Keys are `<epoch>-<seq>-<id>`, so a predecessor's late write always sorts before every key of a later epoch. "Finished" is the leader's journal (`_journal` scans every incarnation's `journal/op/<id>`, a terminal state wins). The Go leader reads entries after the published `ledger_applied` through the bridge (`ledger {after}`), runs them one at a time and checkpoints; module entries (`m-*`) reach it too and each leaves a failed `op/m-<hex>` record. Journals live under each incarnation's `mgr/cephadm/talos/inc/<gid>/journal/` (`op/<id>` and its phases `op/<id>.<phase>`, `roll/<id>.<...>`), the bridge lets a leader write only its own; nothing prunes them. An uncertain job (started, ended, no result) holds back other jobs on its node, and on the leader it never reaches a terminal state (`abandon` returns it unchanged, `unstick` never fails an uncertain phase), so every later ledger operation waits behind it: the whole ledger, not only the node.

1. **Snapshots of the fold.** The active module compacts its ledger when more than 1000 entries follow the newest snapshot (and at most hourly).
   - **The cut** is the largest key `K` such that every operation entry at or below `K` is finished (a terminal journal state), at or below the published `ledger_applied` and not pinned, and every module entry at or below `K` names such an operation. Pinned: the start of a Ceph or agent upgrade until its record in the published state is finished (its steps read `op/<start>.*` and the bridge authorizes the upgrade by its start entry), and any operation a later step or recovery still reads (below).
   - **The snapshot** holds everything a reader derives from the ledger's history, not only today's fold: the fold's state (hosts, daemons, generations, uuids, creations, maintenance, upgrade, RGW certificates, renewals and retirements, agent upgrade, ingress), the fold's `positions` of every covered operation the fold still references (an operation's module entries can follow the cut, beyond an unfinished one), the accepted RGW port (`_rgw_port` reads the history today; it becomes fold state), the highest sequence number per incarnation it covered (later takeover cutoffs take them as seen), the number of entries it covered, and a lookup table of the covered operations (id, kind, host, daemon, request uuid and inputs hash, journal state) for `orch talos operation` and `orch talos request`, kept for 30 days by acceptance time. Every other reader of the raw history moves to fold state with it.
   - **Publication** is immutable and per cut: `cephadm-talos/ledger-snapshot/<K>/<i>` chunks and `cephadm-talos/ledger-snapshot/<K>/manifest` (the writer's gid and epoch, the chunks, their sha256), written once; there is no shared manifest to overwrite. A reader takes the snapshot with the highest `K` whose chunks verify and which is valid: no later valid takeover set a cutoff for an incarnation below the sequence number the snapshot covered for it (a stale predecessor's snapshot that folded its own late writes is rejected), then the entries above it. An entry at or below `K` written after the snapshot can only be a predecessor's late write (an older epoch), which the takeover's cutoffs exclude anyway.
   - **Deletion is delayed and fenced.** The entries at or below `K`, and older snapshots, are deleted only by a later compaction run at least 10 minutes after the snapshot `K` was published, by a module that confirms its leadership right before (`still_active`, a fresh mgr map) and finds `K` still the highest valid snapshot. Config-key has no compare-and-set and Ceph's mgr blocklist covers RADOS, not mon commands, so the fence rests on this: a mgr that lost its leadership respawns as soon as it sees the new mgr map (the monitors send it on its session), and a mgr cut off from the monitors cannot write; a deleting module must have kept its monitor session through 10 minutes without seeing a newer mgr map. That residual window is accepted and documented.
2. **Reading by key, and backpressure.** `Ledger.open` lists the keys above the snapshot in pages (`config-key ls` reduced in the mgr, as `revocation.list_keys`) and reads them by key in bounded batches of `config-key get` over the listed keys, checking that every listed key was read (the revocation reader's `dump_bounded` splits prefixes by decimal digits and cannot split ledger keys, which have `-` after the epoch), so the ledger's size no longer meets the output limit. The module accepts no new operation while more than 500 operations are unfinished, with the reason; the leader's own module entries and the controls (`--resume`, `--stop`, upgrade pause) are not refused. "Unfinished" is computed from one index of journal states built per call (one scan of the journals, not one per operation).
3. **Journal pruning, by the module.** The bridge lets a leader write only its own incarnation, and only the module knows what a snapshot covers, so the active module prunes: with the delayed deletion of item 1 it deletes, in every incarnation, the journal records of the operations the snapshot covers (`journal/op/<id>`, `journal/op/<id>.*`), except what is still read: `journal/roll/<id>.*` stays until the fold retires that roll's certificates (an RGW roll publishes its target before it is applied, and later ingress and renewal operations read an old roll record to finish a half-done one; a renewal's until its `done` entry; a mgr removal's `roll/<id>.certs` until its `retire`). An earlier incarnation's `journal/takeover` stays while that incarnation's published state is the newest (`choose_incarnation` and the leader's `stateSource` pick a predecessor by it until the successor has published its own), and its whole `journal/` goes only once a later incarnation has published and nothing in it belongs to an operation above the snapshot. A takeover's journal import then finds no record of a covered operation, and it skips any whose ledger entry is at or below the snapshot's `K` (finished by definition), so a predecessor's older record is never brought back. The Go leader skips module entries (`m-*`) without a journal record and checkpoints past them.
4. **`cephadm-talos resolve <host> <operation>`** (operator certificate, `POST /v1/resolve` on that agent, with the agent's operation id as the leader's journal names it, for example `op-<hex>.prep`; listed by `cephadm-talos ps` or the suspension receipt's unresolved operations). The agent, holding its grant slot, checks that the operation is a job's, `uncertain` or `started`, that no apply intent is open and that its container has ended (status completed or failed, or neither document nor instance left: `Node.ended`); then, after that, reads the job's outcome again (`JobOutcome`: the job writes its result right before it exits, so one that ended between a reconcile and this check has its result now), and only if it is still without a result marks the operation failed (`rc -1`, "resolved by the operator") and writes the job's tombstone (so it can never run); a result found is recorded as any outcome is. Otherwise it refuses with the reason. Only failed: a done preparation needs its result (the OSD id and uuid), which the operator cannot supply safely. The leader's next query then finds a terminal state: a preparation fails the OSD creation (the existing `failCreate` cleanup, the operator purges the half-made OSD with `ceph osd purge-new` and adds it again), a zap fails the OSD removal, a probe fails the upgrade start; the job's document is then removed by the leader's acknowledgement as for any ended job, and the ledger moves on. `/v1/resolve` is among the operator's calls a fail-closed agent still serves, and it is served while suspended.
5. **Docs.** docs/architecture.md: snapshots and reading by key, backpressure, journal pruning, `resolve`; the Known gaps entries on the ledger's size and on uncertain jobs go.

Codex round 1 of this design (2026-11-04), fixed: snapshots immutable per cut, readers reject one that covers a later takeover's cut-off writes, deletion delayed 10 minutes and fenced by a fresh leadership check (the residual window documented); upgrade starts pinned until their upgrade ends; a predecessor's takeover record kept while its state is the newest published; roll records kept until their certificates are retired; the snapshot keeps referenced operations' positions and the RGW port, and every reader of the history moves to fold state; `resolve` reads the outcome again after the container ended.

## Step 5 design: drain, best-effort noout, identity-based TLS, host set-addr (2026-11-04)

Today (inventory): `drain_host`, `stop_drain_host` and `update_host_addr` are not implemented (Ceph's base class raises). Removals refuse an RGW whose host runs a keepalived (re-apply the ingress without it) and the active mgr (no failover in removals; only maintenance's stop fails the mgr over, bridge `_mgr_fail`). The leader sets noout for maintenance from the state's `Host.NoOut` and unsets it on exit whenever the state says so (ledger.go `stopHost`, `startHost`), not knowing whether the operator had set it before. The agent watches nothing on its node; it talks to the module only for confirmations (`POST /v1/confirm` on 4722). Every TLS client but the leader's bridge call also verifies the peer's address against the certificate's IP SAN (Go's default verification with the address as host; the module's `check_hostname`), besides the identity check; admission checks a changed generated RGW certificate against the node's current Talos addresses and hostname, and exempts retained, unchanged documents (step 1). Neither the fold nor the state can change a host's address after `add_host`.

The step is built in two parts: A (items 1 and 2) and B (items 3 and 4), each with its own Codex loop and live check.

1. **`ceph orch host drain <host> [--zap-osd-devices]` and `drain stop`** (C6).
   - **Acceptance.** `drain_host {host, zap}`, a host kind, refused with `--force` or `--keep-conf-keyring`, for a host in maintenance, while an upgrade, an agent upgrade, an ingress apply or another drain is unfinished, for the active mgr's host when no standby exists, for the last mon or mgr host, for a mon host whose removal would leave fewer than three mons (the rest must keep quorum while its mon goes), and for a host of the ingress (a keepalived runs there: re-apply the ingress without it first, as removing its RGW is refused today; the ingress spec keeps one owner). This is cephadm's behaviour too: its `drain_host` refuses a host named explicitly in any service's placement ("Please update those specs to not list this host", `src/pybind/mgr/cephadm/module.py`), and our ingress always names its hosts; confirmed with the user (2026-11-04). The fold marks the host draining; while it lasts the module accepts no new daemon or OSD there, no maintenance and no set-addr of it.
   - **The leader** records `Host.Drain {op, zap, step, stopped, paused, error}` in the state and runs its steps between ledger operations, one at a time, as an upgrade's (a drain takes as long as its data moves and must not hold the ledger): (a) every OSD of the host marked out at once (one journaled step, so data moves once, not once per OSD onto the next OSD of the same host), (b) each OSD's removal by the existing removal phases (drain until safe to destroy, purge, `--zap-osd-devices` as `osd rm --zap`), (c) its RGWs, (d) its mgr, failed over first when it is the active one (`_mgr_fail` accepts a drain's step), (e) its mon, removed only while the rest keep quorum (the bridge's existing check), (f) a module entry `drain_done {of}`; the host stays enrolled with its agent (`host rm` removes it). Each step is journaled under the drain (`<op>.d<n>`); a step that fails pauses the drain with its reason (`TALOS_DRAIN_PAUSED`), `ceph orch host drain <host>` again resumes it; `ceph orch host ls` shows the host as draining.
   - **`drain stop`** is accepted as `drain_stop {drain}`, a control run ahead of queued operations as upgrade controls are: no new step starts, a step in progress finishes, the fold drops the draining mark. OSDs already marked out stay out (`ceph osd in` is the operator's), as with cephadm.
2. **Best-effort noout on a reboot or shutdown outside the orchestrator** (C7).
   - **Ownership in the fold.** Per host the reasons the module holds noout for (`maintenance`, `unplanned`) and whether the operator owns the flag. Maintenance's noout moves from the state's `NoOut` to these reasons: the leader's `noout set` and `noout unset` calls name the reason; the module sets the flag when the first reason appears and unsets it when the last goes, through its existing per-host command queue (`osd set-group noout` on the host's CRUSH bucket, refused for ambiguous names as today), and records it durably in two module entries: before the command, an intent `noout_intent {of, host, reason, on, prior}` with the flag's state it observed (from the OSD map's flags of the host's CRUSH bucket), then, after Ceph answered, `noout {of, host, reason, on}`. A successor that finds an intent without its completion reads the flag again and reconciles: a set intent whose flag is now set completes as the module's (its recorded `prior` says it was unset), one whose flag is unset is sent again; an unset intent likewise; so a module that died between Ceph's change and its record never turns its own flag into the operator's. A flag already set when the first reason appears is recorded as the operator's and never unset; `ceph orch talos noout keep <host>` hands one over (reasons dropped, never unset). An operator who sets it while a reason holds, without `keep`, has it cleared with the last reason (documented).
   - **The agent's signal.** The agent watches its node's `MachineStatus` (a COSI watch on its own socket); when the stage becomes `rebooting`, `shuttingDown`, `upgrading` or `resetting` (set at the start of Talos's sequence, before containers stop), and again on every later stop sequence's `START` it sees on the same boot (Talos keeps the stage after a cancelled sequence, so a later reboot changes no stage), it sends `POST /v1/going-down {boot}` to the active module on 4722 with its agent client certificate, at once and retried until its stop timeout. It knows where the active module is from the module's status poll, which names the polling mgr and its address (the agent connects by that mgr's certificate identity, so a wrong address only fails). The module checks the peer's identity (agent of a known host), records an unplanned stop (`host_down {host, boot}`) and adds the reason.
   - **Coming back.** After the boot the agent reports its new boot id in its status record; once every OSD of the host is up again, the module drops the reason (`host_up {host}`). A sequence that aborts without a reboot is reported cancelled only on evidence: the agent also watches Talos's machine events on its socket (`os:admin` may) and follows each stop sequence (reboot, shutdown, upgrade, reset) by its events: a `SequenceEvent` `START` opens it; Talos emits `STOP` without an error when a sequence's run returns, then a `NOOP` carrying the outcome: `CANCELED` when another sequence took over (a reboot may replace a reboot); any other error, `FATAL` included, makes Talos shut its services down and reboot (a successful reboot task itself reports one), so it is never evidence of a cancellation. The agent reports the stop as cancelled only when, on the same boot, every stop sequence that started has ended with a `CANCELED` outcome and no stop sequence has started for 60 seconds since (a replacement's `START` follows its predecessor's cancellation at once); Talos leaves `MachineStatus` in the stop stage then, so the stage alone proves nothing. No timer clears it (Talos runs shutdown hooks with their own timeouts before it stops containers, and a long one is a valid shutdown); without the evidence the operator releases it with `ceph orch talos noout release <host>` (the unplanned reason dropped; the flag unset if no other reason holds and the module owns it). A host still down after 30 minutes raises `TALOS_HOST_DOWN` (its noout stays until it returns, the operator clears it, or the host is removed). The daemons never depend on the agent.
   - **Limits** (documented): it only notifies, no ok-to-stop; a power loss, panic or hard reset gives no signal (Ceph's down-out interval applies); two hosts at once can still lose mon quorum.
2b. **Using the stop signal's head start** (added 2026-11-04 at the user's request: we know a stop seconds before Talos stops containers, so we do more than cephadm can; part C, after part B). Both are best effort, as the signal is.
   - **The active mgr fails over at once.** When the stopping host runs the active mgr and a standby exists, the module, on recording `host_down` for its own host, fails itself over (`mgr fail` with its own gid) instead of leaving Ceph to notice after the beacon grace (about 30 seconds). The noout is not set first by this module: the successor's noout loop sets it from the fold's `host_down`, so the failover is not delayed by it.
   - **The mgr and the mon outlive their host's stop signal** (found by part C's live checks, 2026-11-04). When the active mgr's host stops, the agent's `going-down` to its own host's module was lost (`connection reset`, then `connection refused`): mgr.sh and mon.sh end with `exec`, so ceph-mgr and ceph-mon are their container's PID 1, and the SIGTERM Talos sends to PID 1 at the stop makes them exit at once (ceph-mgr's handler `_exit`s); on a mon host the mon's exit also starts an election that stalls the module's ledger write. An earlier reading that Talos signals every process of the container (`WithKillAll` in its runner) was refuted by a test on the combined build (a session working in the Talos repository, 2026-11-04): only PID 1 is signalled, as with Docker, so a trapping entrypoint works. A guard container relying on the shutdown order was tried and reverted. The fix: mgr.sh and mon.sh no longer `exec` their daemon; they run it as a child, install a TERM handler (a container's PID 1 ignores signals it has no handler for), and on SIGTERM wait a few seconds (the mgr 4, the mon 6, so the mon keeps quorum until the module's `host_down` and failover are done), then forward SIGTERM to the daemon and wait for it, its exit status becoming the container's; the delay stays well under the stop timeout (Talos's default 10 seconds; both get an explicit 20 seconds). Every stop of a mgr or a mon (a restart, a redeploy, maintenance, an upgrade) takes those seconds longer; a child that exits by itself (a crash, ceph-mgr's respawn after `mgr fail`, which `exec`s the same process) ends the wrapper with its status as before.
   - **The VIP needs nothing more.** Talos stops containers in the reverse order of `dependsOn` (the shutdown order of the stop-timeout change, upstream since 6d2f793b7 and in the combined build), and each host's keepalived depends on its RGW (daemons.go), so keepalived stops first; it is started with `exec` and releases the VIP on SIGTERM with a priority-0 advertisement, so a peer takes it after the short VRRP skew time, before the RGW stops (a direct `talosctl restart` of one container bypasses the order, as it should). An earlier version of this item added a release file tracked by keepalived; it was dropped (2026-11-04) once this ordering was checked: it solved a problem the shutdown order already prevents.

   Codex round 1 of item 2b (2026-11-04), fixed: the release file on a user volume Talos creates and records-init prepares at every boot (a host path must exist and `/run` is tmpfs); a new image's document layout installed by a second self-update rendered by the new agent, the release used only once the ingress hosts' agents report the mount.

   Codex round 2 of item 2b (2026-11-04), fixed: records-init prepares the volume only when mounted (the first update runs the old layout); a host is done only with the target's layout, checked when verifying done hosts, so a new leader revisits hosts an old one marked done by image; the release puts keepalived in FAULT (track file weight 0, a priority-0 advertisement) instead of lowering its priority, which would wait for the peers' master-down timer.

3. **Identity-based TLS** (E1, the trust part). Every client verifies the peer's chain against the agent CA, its role and host identity (URI SAN), its validity and the revocation list, and no longer its address: Go clients set `InsecureSkipVerify` with a `VerifyConnection` doing the chain verification itself (`x509.Verify` against the agent CA, server use) besides the existing identity and list checks (leader to agents, agents' confirmations to the module, the CLI's operator calls, handoff, restore's check); the module's clients keep `CERT_REQUIRED` and drop `check_hostname` (poll, heartbeat, list delivery), the identity check after the handshake already being there. The leader's bridge call keeps its host-name check on loopback. So a host that moved stays reachable before its certificates are reissued. Admission already leaves retained, unchanged documents unchecked against node facts (step 1); the self-update's check of a new server certificate against the node's addresses stays (it is issued after the move, for the new address).
4. **`ceph orch host set-addr <host> <addr>`** (E1, the address change).
   - **Acceptance.** `set_host_addr {host, addr}`, a host kind, refused while the host is in maintenance or draining, while an upgrade, an agent upgrade, an ingress apply or another move is unfinished, for an address another host has, for a mon host when fewer than three mons exist (its mon leaves and rejoins while the rest keep quorum), and for an address of another family than the old one (Ceph's bind families follow the mons' addresses, daemons.go `CephConf`, and keepalived is IPv4 only); several mons at once or a cluster without quorum are never attempted. The fold records the move as pending (`moving {host: addr}`), not yet the host's address: certificates the module issues keep naming the old one until the leader confirmed the node has the new one.
   - **The move record.** The leader records `Host.Move {op, from, to, step, moved, paused, error}` in the state and runs the move's steps between ledger operations, as a drain's, the module refusing every other operation on the host meanwhile; a step that fails pauses the move with its reason (`TALOS_HOST_MOVE_PAUSED`) and `ceph orch host set-addr <host> <addr>` again resumes it (a control of the move); the record, not the journal, says what is done, and the operation stays pinned against compaction until the record is cleared.
   - **Two addresses during the move.** `Addr` becomes the contact address (the agent, the certificates) once the move is confirmed; each daemon keeps the address it runs on until its own step moves it (`moved` lists them; renders take `from` for the others), so a revision of the host during the move restarts nothing on a new address unasked. Both addresses should be on the node during the move and the old one removed after it; if the old one is already gone, the move still works, as its steps reach the agent at the new address.
   - **Steps.** (a) Confirm: the leader reaches the host's agent at the new address (identity-based TLS, item 3) and checks that its node report lists the address; otherwise the move pauses. Then a module entry `addr_moved {of}` makes it the host's address in the fold, `Addr` switches, and the published inventory follows. (b) RGW: the host's keepalived removed, generated RGW certificates naming the new address rolled to the host's RGWs, keepalived's unicast peers re-rendered on the other ingress hosts, and only then the host's keepalived restored with its new source address, so no two keepalived instances miss each other's advertisements. (c) mgr: failed over first when it is the active one, then moved. (d) OSDs: under a noout reason `move` for the host (item 2's ownership), moved together as maintenance stops them, the reason dropped once they are up on the new address. Moving a mgr or an OSD is more than a new `ADDR`: their scripts leave the address to Ceph, which picks it from its configuration (`pick_address.cc`), so with both addresses on the node a restarted daemon can keep advertising the old one; each moved daemon gets `public_addr` (an OSD also `cluster_addr`) set to the new address in the monitors' configuration database (a bridge call of the move), and its step completes only when the OSD map shows an OSD advertising the new address, and for the mgr, which the mgr map shows with an address only while it is active, when it is back as a standby (a new gid) after its restart with `public_addr` set; its address is the one Ceph uses when it becomes active. These per-daemon settings outlive the daemon in the configuration database and Ceph reuses freed OSD ids, so removing an OSD or a mgr clears its `public_addr` and `cluster_addr` before the id is purged, and creating an OSD clears any left for its id before it starts. (e) mon: it leaves the monmap (`mon rm`, the existing quorum check), is deployed again as a new generation with a fresh store at the new address (it joins from `mon_host`) and is awaited in quorum. (f) `mon_host` in every host's `ceph.conf`. (g) The host's agent and mgr certificates reissued for the new address (A1's paths, as steps of the move). (h) A module entry `addr_set {of}` (idempotent), then the record cleared, which releases the pin, as an upgrade's end is recorded before its record goes.
   - **The active mgr's host.** The module heartbeats its own host's agent over loopback (identity-checked as before), not at the host's published address, so a move of the active mgr's host never cuts the leader off from its agent.
5. **Docs.** docs/architecture.md: drain, noout ownership and the agent's signal, identity-based TLS, set-addr; docs/capabilities.md rows for `drain_host`, `stop_drain_host`, `update_host_addr`; SHORTCOMINGS and ROADMAP entries they settle.

3. Only the cephadm-talos agent mints Talos credentials, in the leader's agent through its own socket, short-lived and in memory only; the mgr never sees one. The leader's agent reaching other nodes' Talos API for enrollment and repair is an accepted rule change. On a control-plane node a compromised leader host could already mint them; what the mode changes is that the module's ledger, which the mgr and `client.admin` can write, now steers those actions, so they stay narrow, checked against the leader agent's own pinned policy, and fenced (C3).
4. `ceph orch host add` alone enrolls in the mode; re-applying the agent's own documents needs no approval.
5. Auto adoption is one cluster-wide opt-in; identity tracking (renames, replacements, address changes) and recovery from the members are the priority of the discovery mode; renumbering is out of scope.

6. A stale CRL fails open with a health warning by default; a fail-closed setting for high-security clusters, in the agent's own policy; NTP tampering is an accepted risk.

7. A compromised mgr host, standby or active, is a compromised cluster: confirmations are not bound to the active incarnation against a lying standby (B).

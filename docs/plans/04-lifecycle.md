# Plan 04: lifecycle of hosts, agents and certificates (roadmap milestone 3, part 3)

Status: draft for sign-off, 2026-11-03. Scope agreed with the user on 2026-11-03 (decisions at the end). ACME for the RGW serving certificate is plan 05.

## Goal

Plan 03 made the cluster changeable through `ceph orch` and left its long-running upkeep to the CLI or to nobody: certificates expire after 3 years and are never revoked, a new node needs the CLI, the agents cannot be upgraded after the handoff, the ledger grows without bound, an uncertain job blocks its node for good, and the leader's identity rests on a heartbeat from its own host. Plan 04 closes those gaps, so a cluster can run for years with the CLI needed only for bootstrap, recovery, approvals and teardown. Two optional modes go further where the Talos cluster allows it: enrollment and repair by the leader (every Ceph node on one Talos CA) and host tracking through Talos cluster discovery. Without them everything works as after plan 03. Milestone 3 is done with this plan.

## Baseline

Plan 03 as built (docs/architecture.md), Ceph v21.2.0, the combined Talos build of PRs #14775, #14781, #14788 and #14795. Every Ceph node is a Talos control plane: Talos containers are not supported on workers (confirmed with the Talos maintainers), so each node's machine config holds the Talos CA key and each agent's machined socket (`os:admin`) can call `GenerateClientConfiguration` (control-plane only, any roles, any positive TTL; it returns the Talos CA certificate with the credential). Talos has no conditional apply: a patch reads the whole machine config, merges and applies it whole (talos.go `Patch`), so two writers can overwrite each other (Known gaps).

## Design

### A. Certificates of the cluster's own CA

1. **Renewal by the module.** The module checks every certificate of the cluster state once a day and renews each that expires within 30 days, as cephadm's certificate manager does. It accepts each renewal as a ledger operation of its own (`renew <kind> <name>`), which authorizes the bridge to release that renewal's new keys and nothing else, so the leader carries it out like any operation and a takeover continues it:
   - mgr certificates: issued by the module (the existing `mgr cert` path), granted as the mgr host's files; the module loads them (item 2);
   - agent certificates: issued by the module, the keys stored as secrets; the leader grants the agent its new document (C2). Depends on C2;
   - generated RGW certificates: issued for at most 1 year from now on (365 days, under the 398 days browsers accept for a server certificate; a setting may lower it), by the CLI and by the module alike (today 2 years in both); renewed 30 days before expiry through the existing reissue and roll of step 6e, triggered by the expiry;
   - the old certificate stays valid until the new one is verified in use (an agent answering with it, the module serving it), then it is revoked (item 3) if it has not expired.
2. **The module reloads its credentials.** Today it reads its server certificate, the CA it trusts and its confirmation signing key only at start; it watches their files and loads them when they change, keeping the old ones on a load that fails.
3. **The operator's client certificate** is the recovery credential. The CLI renews it on any command when it expires within 60 days (reading the agent CA key through exec with `client.admin`, as enrollment does), and the module raises a health warning from 60 days before its expiry, so it is renewed while the mons answer. If it has expired anyway, the CLI's suspension treats an agent refusing the operator certificate for its expiry like an agent that does not answer and suspends that node through Talos (plan 03's item 5).
4. **Revocation.** A certificate revocation list of the agent CA (X.509 CRL; its CRL number only grows), issued by the module whenever a certificate is retired before its expiry (item 1, C5) or on `ceph orch talos revoke <serial>`, and reissued daily with a `nextUpdate` of 7 days. Delivery reaches every verifier, also idle ones: the module sends it with its 30 second status poll to every agent (not only with heartbeats, which go to one agent); successor modules and the CLI read it from config-key at start and per command. Every verifier persists the highest CRL number it saw and refuses an older list, and refuses a peer certificate the list names. Enforcement takes at most one status poll for a reachable agent. An agent whose CRL is past `nextUpdate` (cut off for 7 days) keeps working and reports it (fail open, the default): stale revocation information is an accepted risk; usually a cut-off agent also reaches no mon quorum and gets no confirmation, but that is not guaranteed (status polls and confirmations use separate connections), and a health warning when it returns is enough. For high-security clusters a fail-closed setting: the TLS layer still accepts every certificate of the agent CA, and the agent's handlers refuse every request except the CRL delivery (`POST /v1/crl`, the CRL self-authenticating by the agent CA's signature, accepted also while suspended) and the operator's calls (suspension and recovery); normal access resumes once a newer CRL that is within its `nextUpdate` is installed. The setting is part of the agent's own policy, set by the CLI at bootstrap or by an approval the operator signs, never by the module or the cluster state: the agent keeps it in its records as well as its document, and a document (a restore, a repair, plan 03's resumption rendering it from the state) can only make it stricter; only an approval the operator signs turns it off. The CLI's recovery journal and `local.json` keep the bootstrap choice, so documents the CLI renders carry it. Time comes from the node's clock (Talos's time sync): a tampered NTP server is an accepted risk. The CRL is signed with the agent CA key, which the module holds: it protects against stolen leaf keys, not against a compromised mgr, which can issue certificates anyway (Known gaps).
5. **Rotation of the agent CA and of the operator's approval key** stays in milestone 4 (both need an overlap in which old and new are trusted, built on item 4's delivery).

### B. The leader's identity: an accepted risk, no change

A standby mgr has a CephX key of its own with the same caps and config-key access as the active one and becomes active with one `mgr fail`, so a compromised mgr host, standby or active, is a compromised cluster. Binding confirmations to the active incarnation against a lying standby (ROADMAP milestone 4) defends no real boundary and is not built: the agents get no Ceph identity of their own, and confirmations, heartbeats and the leader-only endpoints stay as plan 03 built them (they fence a stale leader, which is about correctness). With this plan, docs/architecture.md's Known gaps entry on confirmations becomes an accepted risk (every mgr host is trusted as the active mgr is), and ROADMAP milestone 4's items for it (the incarnation evidence, bound confirmations, leader-only endpoints) are dropped, keeping the delivery of revocations (A4).

### C. Hosts and agents

1. **Agent document updates.** The agent's document (its image, certificates, policy inputs) is the CLI's after the handoff. It becomes updatable through the agent itself: the leader grants an agent document, confirmed as any grant, and the agent applies it to its own node only if it passes the agent's own policy, which no grant can change: the image in the operator's approval, the same host identity and agent CA, the same approval key (a new one only when an approval signed with the old one names it), certificates the agent CA issued for that host, and no other field changed. The apply restarts the agent; its apply intent, recorded first, is decided by the next start's reconcile.
   - **Self-upgrade:** the image is pulled on every node first (Talos image pull through each agent); then every non-leader agent, one at a time, each answering on the new image before the next; then the active mgr fails over and the old leader's agent goes last.
   - **Known good:** the state keeps the previous agent image and approval of it; `cephadm-talos agent restore <host>` (operator, CLI) or repair (C4, in the mode) renders the agent's document from the current certificates with that previous image, never an old document whole (it would bring back revoked certificates). The agents' records keep one schema within a release, so a rollback reads them.
2. **Enrollment by the leader (optional mode).** A cluster setting (`mgr/cephadm/talos/leader_enrollment`, off by default), accepted only after the leader proved the condition: every host of the cluster answers with a Talos server certificate of the CA its own node's `GenerateClientConfiguration` returns. With it on, `ceph orch host add <name|addr>` needs no enrollment record:
   - the leader mints a Talos credential through its own machined socket (`os:admin`, 10 minutes, memory only; never in config-key, the journal, the ledger or a log), connects to the target, verifies the target's Talos server certificate against that Talos CA, then reads the node's identity over the connection (hostname, node id, Talos version, CPU flags) and runs the CLI enrollment's checks (version, x86-64-v3, a lowercase hostname, a node without an agent of this cluster);
   - the agent's documents it applies pass the leader agent's own policy (C1's checks, against the leader agent's pinned approval key, agent CA and repositories, an approved image): the cluster state alone cannot change what gets applied;
   - the handoff: the new agent's document carries a one-time enrollment nonce; the leader presents it on `POST /v1/handoff` with its agent client certificate (the leader role), the fresh agent adopts its node (nothing to adopt) at revision 1 and records the nonce as consumed, and the leader removes the nonce from the document with its first revision. An agent whose records are lost later finds no nonce and stays unowned (plan 03's missing-records rule), for the operator.
   - Without the mode, `cephadm-talos host add` enrolls as today.
3. **Remote writes keep plan 03's guarantees.** The leader writes to another node only an agent's own documents, for enrollment (C2), repair (C4) and removal (C5). An agent that stopped may still have an apply of its own in flight (Talos finishes an apply after its caller is gone, and a whole-config apply could undo the leader's), so before writing to a node with an agent of this cluster the leader takes it over the way plan 03's suspension does for an agent that does not answer (item 5, suspend.go): it removes the agent's document if present, waits until every instance is gone, reads the agent's records with a records job, and waits until an apply intent there has settled (`ApplySettle` on that boot); only a fresh node (no agent, no records of this cluster) skips that. Each remote write:
   - is recorded first as a remote intent in the leader agent's records (like a bridge intent: target, documents, time), so a suspension's receipt lists it and the CLI's recovery reserves the target node;
   - is preceded by the leader's check that its incarnation is still active (a fresh `mgr dump` through the bridge, as before every grant), and serialized per target node (one at a time, across incarnations: a successor takes over a predecessor's remote intents from the journal);
   - is sent on a connection of its own, dialled for it and closed after it, with a last-dispatch deadline of one minute after the intent (Talos checks a certificate when a connection is established, not per call, so the credential's expiry alone does not bound an open connection; the deadline is enforced as the CLI's apply deadline is, talos.go), and is decided afterwards by reading the target's config (the documents with the expected hashes); one whose outcome is unknown reserves the target node until `ApplySettle` after its last-dispatch deadline, then is decided from the config, as an agent decides its own uncertain apply.
   - Remote writes run in the leader's tick, so a suspended leader agent sends none, and none goes to a node whose agent's suspension the CLI recorded.
4. **Repair (in the mode).** The leader runs in the active mgr's agent, so a failed leader agent cannot repair itself: the module fails its own mgr over (`mgr fail` of itself) once its local agent has not answered a heartbeat for 2 minutes and a standby is available, so a standby's agent becomes the leader and repairs the old one; without a standby, a health warning and the CLI (`cephadm-talos agent restore`). Repair itself: A host whose agent has not answered for 10 minutes while its node answers through Talos (its agent document missing, crash-looping or stopped) gets its agent documents applied again, rendered from the current certificates and the known-good image if the current one is the one failing, through C3's rules. Re-applying the agent's own documents is not destructive and needs no approval. Never while the cluster is suspended or the host is in maintenance.
5. **Removed hosts.** `host rm` (after its daemons are gone): the leader grants the host's agent its retirement, confirmed as any grant; the agent records it, removes its own documents (agent and records-init; the records volume stays) through its own socket and stops. Once it no longer answers (and, in the mode, its documents are gone from the node's config, read through C3's connection), the module revokes its certificates (A4) and deletes its keys. An agent that does not answer the retirement: in the mode, the leader removes its documents through C3 once it has not answered for 10 minutes; without it, `cephadm-talos host forget <host>` does (the CLI's own documents).
6. **`ceph orch host drain <host>`** and `drain stop`: the drain is a fold state of the host (draining), accepted once; while it lasts the module accepts no new daemon on that host. The leader removes the host's daemons one at a time through the existing removals (RGW with its keepalived first, the mgr after a failover, a mon only while the rest keep quorum, OSDs through their drain), each as its own step journaled under the drain operation, checking between steps whether the drain was stopped. `drain stop` is accepted as a control of the drain (as upgrade controls are, ahead of queued operations): no new step starts, a step in progress finishes. `--zap-osd-devices` is supported (as `osd rm --zap`); `--force` and `--keep-conf-keyring` are refused.

7. **A Talos reboot or shutdown outside the orchestrator (best effort).** noout ownership: the fold keeps, per host, the reasons the module set noout for (maintenance, unplanned stop); the module sets it when the first reason appears and unsets it when the last one goes (maintenance exit included, which today unsets whenever it set it, ledger.go), through the module's existing per-host noout command queue. Ceph's flag has no owner: if the host's noout was already set when the module's first reason appeared, the module records it as the operator's and never unsets it. An operator who sets the flag while a reason of the module holds cannot be told apart from the module's own; `ceph orch talos noout keep <host>` hands it over (the module drops its reasons and never unsets it), and without it the module clears it when its last reason goes (documented). A sequence that aborts without a reboot: if the agent is still up on the same boot 15 minutes after its report, it reports the stop as cancelled and the reason goes. Then: A plain `talosctl reboot`, `shutdown` or `upgrade`, a reboot after a config change or the power button sets no `noout` today, so the host's OSDs are marked out after `mon_osd_down_out_interval` and data moves. The agent watches its own node's `MachineStatus` through its socket; when the stage becomes `rebooting`, `shuttingDown`, `upgrading` or `resetting` (Talos sets it at the start of the sequence, before it stops containers), the agent tells the module over its existing channel to the module (`POST /v1/going-down`, its agent client certificate), and the module runs `osd set-group noout` for the host's CRUSH bucket (the command maintenance uses, refused for the same host names) and records an unplanned stop of that host in the fold, apart from a maintenance. After the boot the agent reports its new boot id; once the host's OSDs are up again, the module clears the noout, only one it set itself and only if no maintenance or operator set it meanwhile. The stage changes before Talos stops containers, so the message normally goes out first; the agent sends it at once and retries for its stop timeout. The daemons do not depend on the agent (that would keep them from starting while the agent is down). Limits: it only notifies (no ok-to-stop, the reboot is Talos's); a power loss, panic or hard reset gives no signal (Ceph's down-out interval applies); two hosts going down at once can still lose mon quorum; a host that never comes back keeps its noout until the operator clears it or removes the host (a health warning after 30 minutes).

### D. The ledger and journal

1. **Ledger compaction and its size.** The module folds finished operations into a snapshot (the fold and the takeover cutoffs at a sequence number), chunked against the config-key entry limit as the cluster state's records are, published under its sequence number before the folded entries are deleted; a reader takes the newest complete snapshot and the entries after it. The module reads the ledger by key (list, then get) instead of one dump, so its size no longer has the 256 KiB limit, and it accepts no new operation while more than 500 are unfinished (backpressure, with the reason). The request-uuid lookup of `orch talos request` keeps its window over the snapshot.
2. **Journal pruning.** The leader deletes a finished operation's journal records once the published state's `ledger_applied` is past it, and a takeover's journal import skips every operation whose ledger entry is at or below the newest snapshot's sequence number (finished by definition), so a predecessor's older record of a pruned operation is never brought back.
3. **Resolving an uncertain job.** `cephadm-talos resolve <host> <operation>` (operator certificate, `POST /v1/resolve` on that agent): the agent marks the job failed and runs jobs again, but only once it is sure the job cannot still run: no document and no instance left, no apply intent open (the same conditions as its reconcile). Only failed: a done preparation needs its result (the OSD id and uuid), which the operator cannot supply safely, so the creation fails and the operator cleans up (`ceph osd purge-new`) and adds the OSD again.

### E. Talos cluster discovery (optional mode)

The leader's agent reads the Talos `Member` resources of its cluster from its own socket (`os:reader`): node id, hostname, machine type, Talos version and addresses. On when discovery is enabled on the nodes (it works without Kubernetes); without it, hosts are tracked as today. Discovery is a hint: a node is the cluster's host only after it was authenticated (C2, or the CLI's enrollment), and members expire only after discovery's 30 minute TTL, so a departure warning complements the agents' heartbeats (stale after 2 minutes) and never replaces them.

1. **Identity.** Enrollment records each host's node id. Changes are classified and reported as health warnings, with what follows:
   - **gone**: a host's node id leaves with no successor: `TALOS_HOST_GONE`, always;
   - **rename**: the same node id under another hostname: `TALOS_HOST_RENAMED`; the host keeps its Ceph name (daemon ids, certificates). Admission checks a generated RGW certificate against the host name in the agent's own identity (its certificate, the Ceph name), not the node's current Talos hostname (node.go, admit.go), so RGW and keepalived revisions of a renamed host keep passing;
   - **address change**: a known node id with a new address. First the trust: the leader and the module verify agents and mgrs by their certificate's identity (URI SAN), not by IP SAN hostname verification as the leader does today (leader.go), so a moved host stays reachable before its certificates are reissued. Admission no longer re-checks a retained, unchanged document against node facts that changed since it was admitted (its address, its hostname): it was admitted before and only the node changed; a changed document is checked in full. So the roll that follows a move (keepalived removed first, then the RGW's revision with the new address and a certificate naming it) passes with the RGW still rendered for the old address, also after the old address is gone; the RGW's certificate is reissued and rolled before the mon moves. Then `ceph orch host set-addr <host> <addr>` (implemented, accepted from the operator, or from the leader's report in the leader-enrollment mode) updates the host's address in the fold and the state, and the leader follows, one host at a time while the other mons keep quorum: first the generated RGW certificate naming the new address and keepalived's unicast peers (the roll above), then the mon leaves the monmap and is added again under its name at the new address, then `mon_host` in every `ceph.conf` and the agent's and the mgr's certificates with their IP SANs (A1). Several mons at once (a renumbering) or without quorum: reported, never attempted.
   - **replacement**: a new node id with the hostname and address of a host that left (a reinstall wipes the node identity, new hardware has its own): `TALOS_HOST_REPLACED`, naming the successor. Identity is read from the affiliates (one per node id), not the members, which Talos builds by node name (member.go), so two machines with one hostname show as two affiliates. Discovery is no fencing: an affiliate that expired may be a partitioned machine still running its daemons. `ceph orch talos replace <host> --old-node-is-gone` (operator only, never automatic, the operator's statement that the old machine is wiped or off) runs a protocol of its own, since the successor has none of the predecessor's records: the old host's agent certificates are revoked and its sessions closed; its operations whose outcome is unknown are failed (their node is gone) and its reservations released; the host leaves maintenance in the fold if it was in it; then the successor is enrolled under the same name as a new generation of the host (C2 in the mode, `cephadm-talos host add --replace` without), and its daemons are deployed again: OSDs whose disks carry this cluster's BlueStore label with the OSD's uuid from the state are activated from the label, its mon is added again (a fresh store that syncs), its mgr and RGW deployed again.
2. **Enrollment by name.** In the leader-enrollment mode, `ceph orch host add <hostname>` takes the address from the members.
3. **Auto adoption (opt-in).** `mgr/cephadm/talos/auto_adopt`, for clusters where Ceph runs on every node: every new control-plane member is enrolled as with `host add` (a replacement is not: it waits for the operator, E1); reported by the leader to the module, which accepts the operation itself. Needs the leader-enrollment mode.
4. **Recovery.** The CLI's contacts come from the members when `local.json` is gone: `--node <addr>` with any talosconfig of the cluster finds the rest.

## Tests

- Unit: renewal and the ledger operations it accepts, key release bound to them; the module's credential reload; the operator certificate's warning and the expired-certificate suspension path; CRL issue, ordering, delivery by status polls, persistence, refusal; agent document admission against the agent's own policy; self-upgrade order and restore; remote intents in receipts, serialization, settlement; snapshot chunking, reads by key, backpressure; journal import skipping compacted operations; `resolve` refusing while the job could run; drain steps and stop; the going-down report, the unplanned stop in the fold and clearing only its own noout; member classification; the replacement protocol.
- Integration (QEMU): certificates renewed by the module (agent, mgr, RGW) with no lost confirmation; a revoked agent certificate refused everywhere within a poll; agent self-upgrade across all hosts with a failover, and a new image that does not start (restored); `host drain`, a `drain stop` mid-way, a plain `talosctl reboot` of an OSD host (noout set before its OSDs stop, cleared after they are up, no data movement), then `host rm` and the host's certificates refused afterwards; leader enrollment with `ceph orch host add <name>`; repair of a deleted agent document; a node's address changed and followed; a reinstalled node replaced after the operator's statement, its OSDs activated from their labels; a host's retirement removing its own agent; auto adoption of a new node; recovery of the CLI's contacts from the members; network partitions (the leader's host cut off during a remote write and during a self-upgrade), several simultaneous failures.

## Out of scope

Rotation of the agent CA and the approval key (milestone 4); monmap surgery for a renumbering or a lost quorum; Talos credentials anywhere but in the leader's agent's memory; enrollment by the leader of nodes on another Talos CA (the CLI enrolls them); worker nodes (unsupported for Talos containers); ACME (plan 05).

## Decisions (user, 2026-11-03)

1. Plan 04 is the deferred core; ACME is plan 05.
2. Every Ceph node is a Talos control plane. Leader enrollment and discovery are optional modes; without them everything works as after plan 03.
3. Only the cephadm-talos agent mints Talos credentials, in the leader's agent through its own socket, short-lived and in memory only; the mgr never sees one. The leader's agent reaching other nodes' Talos API for enrollment and repair is an accepted rule change. On a control-plane node a compromised leader host could already mint them; what the mode changes is that the module's ledger, which the mgr and `client.admin` can write, now steers those actions, so they stay narrow, checked against the leader agent's own pinned policy, and fenced (C3).
4. `ceph orch host add` alone enrolls in the mode; re-applying the agent's own documents needs no approval.
5. Auto adoption is one cluster-wide opt-in; identity tracking (renames, replacements, address changes) and recovery from the members are the priority of the discovery mode; renumbering is out of scope.

6. A stale CRL fails open with a health warning by default; a fail-closed setting for high-security clusters, in the agent's own policy; NTP tampering is an accepted risk.

7. A compromised mgr host, standby or active, is a compromised cluster: confirmations are not bound to the active incarnation against a lying standby (B).

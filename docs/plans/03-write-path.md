# Plan 03: the write path (roadmap milestone 3, part 2)

Status: signed off 2026-10-30 (decisions at the end). Revised 2026-10-29 for the four Talos PRs below; roles and security added 2026-10-30.

## Goal

The PoC's commands become `ceph orch` commands. The `cephadm` mgr module (plan 02) takes them, the Go leader carries them out, and each agent applies its own node's documents. Cluster state and keys move into the cluster the way cephadm keeps them. Afterwards the CLI is needed for bootstrap, enrolling a new node, recovery without mons and tearing a cluster down; everything else is `ceph orch`, as with cephadm.

Plan 04 follows with: enrollment by the leader instead of the CLI, daily certificate renewal by the mgr, agent self-upgrade, journal compaction, `orch host drain` and broader failure tests. Milestone 3 is done only after plan 04. Declarative service specs (`orch apply`, except the ingress subset below) and the rest of parity stay in milestone 5.

## Roles and security

This section is the reference for who does what; step 8 turns it into `docs/architecture.md`, kept current from then on.

### Components

| Component | Runs where | Holds | Talks to |
|---|---|---|---|
| CLI (`cephadm-talos`) | the operator's workstation | a talosconfig per node (`os:admin`), the `client.admin` keyring, `ceph.conf`, the fsid, the operator client certificate | every node's Talos API, remotely; agents' operator API (suspension only) |
| Agent | one `ContainerConfig` per Ceph node: `restricted`, uid/gid 50, host network, `machinedAccess`, `FROM scratch`, no Ceph binaries | its server and client certificate and key, the agent CA certificate, its records on the `cephadm-talos` volume. No Ceph key, no talosconfig | its own node's Talos API through the local socket only; the mgr module (confirmations, and the bridge for the leader) |
| Leader | code inside the agent on the active mgr's node; it is the leader only while that mgr's module heartbeats it | nothing extra; the journal and state are in config-key, reached through the bridge | the other agents over mutual TLS (grants), the bridge |
| mgr module (`cephadm`) | Python inside the active `ceph-mgr` | the mgr's CephX key, the mgr's certificates, read/write access to config-key (the agent CA key and RGW CA key are stored there) | the mons, the agents (status, heartbeats, confirmations) |
| Daemons and jobs | Ceph containers on each node | their own keyring, in their document | the mons, Ceph clients |

### What happens when

| Event | CLI | Leader and module | Agent of the affected node |
|---|---|---|---|
| Bootstrap | deploys the first mon, mgr and every agent through the Talos API, imports the keys, writes the state to config-key, enables the module, hands each node over | starts heartbeating the local agent once enabled | starts frozen, acknowledges the revision it finds, owns its node from then on |
| Enrolling a node | provisions the volumes, certificates and agent remotely, hands the node over, runs `orch host add` through exec | records the host | as in bootstrap |
| Steady state | nothing | polls every agent's status every 30s, heartbeats the leader every 5s | reports its containers; changes nothing |
| A change (`orch daemon add`, `redeploy`, `rm`) | optional: runs `ceph orch` through exec in a mgr container | records the operation, renders the documents (reading keys with `auth get` through the bridge), sends the revision as a grant | reserves, asks the module for a fresh confirmation, applies the documents to its own node, watches the result, reports |
| A job (OSD prepare, zap) | nothing | grants the job and its inputs | applies the job document, waits for `completed`/`failed`, reads the result file, removes the document after the leader acknowledged |
| Maintenance, reboot, upgrade | nothing | runs `ok-to-stop` and the other checks through the bridge right before each step; moves the mgr away first if it is the active one's host | stops its daemons or reboots or upgrades its own node, only with a grant and a fresh confirmation |
| mgr failover | nothing | the new active mgr's module heartbeats its local agent, which takes over from the journal | other agents close the old leader's sessions and wait |
| Quorum loss | nothing | no new grants | keeps its daemons running; work it already had confirmed finishes or is recorded as uncertain; nothing new is started |
| `shell` | execs `ceph` in a mgr container (a mon container without mgr), the admin key over stdin | nothing | nothing |
| Recovery without mons, `rm-cluster` | suspends the agents, then works on the nodes directly through Talos with its own local journal | not involved | acknowledges the suspension once nothing it started is running, then does nothing until a new handoff |

### Responsibilities

The agent:
- applies and removes only its own node's Ceph documents, and only with a grant and a fresh confirmation; keeps every other document untouched;
- runs jobs on its own node, reboots or upgrades its own node when granted;
- keeps its durable records (sessions, ownership, operations) and refuses to act when they are missing or damaged;
- detects drift (an owned document changed, missing, or a foreign Ceph document) and then stops applying;
- runs read-only admin socket queries through exec;
- checks every granted document against its fail-closed admission policy (item 13) before applying it.

The agent never: talks to the mons (it has no Ceph key); reaches another node's Talos API; decides on its own to change anything; issues or renews certificates (plan 04).

The CLI: bootstrap, enrollment (until plan 04), `shell`, recovery without mons and `rm-cluster`; otherwise it is a thin `ceph orch` client. It does not patch nodes in normal operation and keeps no inventory.

The mgr module: the `ceph orch` interface, the journal and state in config-key, rendering, scheduling of operations, safety checks, confirmations. Together with the leader it is the only place where decisions are made.

### Security implications

- **An agent is root-equivalent on its own node.** `machinedAccess` gives a container every Talos role on the local socket, whatever role it requests; plan 02's agent asked for `os:reader` but could already have asked for more. Requesting `os:admin` therefore does not change what a compromised agent can do: apply any machine config on its node, start privileged containers, read every keyring in the node's documents (the agent is given no Ceph key, but it can read the local daemons' keys), wipe disks, reboot.
- **On a Talos control-plane node, a compromised agent reaches every node that trusts the same Talos CA.** `os:admin` on the local socket allows `GenerateClientConfiguration`, which signs a client certificate with any roles using the CA in that node's machine config (control-plane nodes only). The resulting talosconfig works against every node of that Talos cluster. The agent's design uses only its local socket, but this is what a compromise yields. Operators who need a node boundary run Ceph on Talos worker nodes, or on nodes whose Talos CA is not shared. A role ceiling for `machinedAccess` (our unfiled draft 03) would not help: applying configuration already needs `os:admin`, the same role that allows `GenerateClientConfiguration`.
- **The leader's node and the active mgr are the most sensitive.** The leader can send grants to every agent, and confirmations prove leadership, not content. A compromised agent on the active mgr's node, or a compromised mgr, can therefore change Ceph containers on every node within the admission policy (item 13), remove daemons and grant zaps, and through the bridge read CephX keys with `auth get`. Those include the mgr's own key, which the leader needs to render mgr documents and whose `profile mgr` caps allow changes to mon auth, so a compromised leader has the mgr's Ceph access; the bridge refuses `client.admin`, but that is no boundary beyond the mgr's caps. This is the counterpart of cephadm's mgr, which holds SSH root access to every host; here no component is given a credential for other nodes' Talos APIs, but see the control-plane point above.
- **The mgr module holds the agent CA key** in config-key. Whoever can read config-key (the mgr, `client.admin`) can issue agent and operator certificates.
- **The CLI's workstation holds full control**: `os:admin` on every node and `client.admin`, as a cephadm admin host does.
- **Secrets in machine config are readable with `os:admin`** on a node (raw machine config needs `os:admin` in the pinned Talos; `os:reader` gets only redacted forms of supported resources) until Talos ships secret volumes (#14221): daemon keyrings and the agent's and mgr's TLS keys. Exec does not add to this: every CLI admin exec, single command or script, sends the admin key over stdin to a wrapper that exports it into the executed command's `CEPH_ARGS`, in a Ceph container (a mgr first), so it is in no file, no machine config and no supplied arguments; Talos audits the command line, not stdin. It is in that process's environment while the command runs, readable to root in that container and on that node. The CLI never adds `--verbose`, debug or tracing options to these commands, which could print or dump the configuration.
- **Exec needs `os:admin`** and is audited by Talos (`container exec started/finished` with the command line and exit code).
- **Fencing is about correctness, not attackers**: it stops a stale leader, not a malicious one.
- **Workload isolation stays off on Ceph nodes** until Talos PR #14603 is released (`docs/support.md`).
- **Network**: port 4721 (agent status and grants, mutual TLS) and 4722 (bridge and confirmations, mutual TLS, the bridge only for the local agent's certificate) on the hosts' network.

## Design

1. **Leader placement.** The Go leader runs in the agent on the active mgr's node. The module's `serve()` heartbeats that agent every 5 seconds over the agent channel with the active mgr's gid (the incarnation) and the agent's session nonce. An agent that (re)starts begins frozen as a follower and reloads its durable records (item 6) before it accepts a heartbeat. Only the active mgr runs the module (no `StandbyModule`).
2. **Ceph bridge.** The module serves a mutual-TLS API on the mgr host's network, port 4722, for its local leader agent only: `mon_command`, config-key get/set, `auth get-or-create`/`auth get`, and tool execution (`radosgw-admin`) with the mgr's credentials. It uses `send_command` with its own completion handling, not `mon_command` (whose wait is unbounded): every call has a deadline, admission and outstanding commands are bounded, and a timed-out call is reported as "outcome unknown"; its late completion is kept for reconciliation. Calls are on an allowlist with fixed argument shapes. Heartbeats and confirmations (item 5) have their own threads, so blocked calls cannot starve them. Shutdown stops admission and waits a bounded time for outstanding calls.
3. **Identities.** The agent CA (plan 02) issues distinct certificates: a server and a client certificate per mgr (`mgr.<id>`), a server and a client certificate per agent (`agent.<host>`), and an operator client certificate for the CLI. Each endpoint checks role, fsid and host in the certificate: the bridge accepts only the local agent's client certificate; the confirmation endpoint accepts the cluster's agents; the agents' operator API (item 11) accepts only the operator certificate. A certificate never implies leadership.
4. **State and keys in the cluster.** Keys live only in the mon auth database: `auth get-or-create` for ordinary identities, the shared `mon.` key for additional mons, `ceph osd new` (through ceph-volume) for OSDs. The leader reads a key with `auth get` when it renders a document; daemon keyrings stay in the deployed node documents. Everything else of `state.json` moves into config-key under `mgr/cephadm/` (the module store, as cephadm keeps `mgr/cephadm/inventory` and `cert_store.*`): hosts, daemons, image and verified version, maintenance and tombstones, RGW and VIP settings, the RGW CA and the agent CA. Mutable state is published as immutable records plus a manifest, both under the leader's incarnation; there is no global "current" pointer. Readers select the active incarnation through the leadership protocol (item 5) and read its manifest. A new leader freezes conflicting publication, reconciles its predecessor's state and unresolved operations (item 6), then publishes its first manifest with that baseline; a delayed write of the predecessor lands under the old incarnation and is ignored. Every record's encoded size is checked against `mon_config_key_max_entry_size` (64 KiB by default in v20.2.4) and larger ones are split into chunks before the manifest names them. The module reads the inventory from this store instead of the node files of plan 02. The workstation keeps what a cephadm admin host keeps: `ceph.conf`, the `client.admin` keyring, the fsid, the talosconfig and context per node, and the operator certificate. `state.json` goes away.
5. **Grants and fencing.** The leader stores each host's desired documents as an immutable revision (item 4) and delivers it to that host's agent over the agent channel. Before an agent changes its node (an apply, a job, a reboot), and before the leader sends a mutating call through the bridge, a reservation for the operation is persisted (item 6), then a confirmation is obtained: the agent sends the module a fresh challenge with the fsid, its session, the host, the revision, the operation id and the hash of the inputs; the module answers only after a fresh `mgr dump` from the mons shows its own captured gid as active, and signs the answer with its mgr certificate. The agent measures the 10 second validity from when it sent the challenge. No answer means no change. A confirmation is a point-in-time check, not a lock, so takeover (item 6) covers what an old leader may have left behind.
6. **Durable records and takeover.** A `cephadm-talos` user volume (`/var/mnt/cephadm-talos`, outside the cluster data that `rm-cluster --zap` deletes) is provisioned with every host's documents and mounted into the agent and the jobs. Talos keeps the volume root at uid/gid 0, mode 0755, and resets that on every mount, so a `records-init` container (`restart: {policy: on-failure, maxRetries: 3}`, `restricted` with only the capabilities `chown` needs, CHOWN and FOWNER, verified in the spike; `privileged` only if that fails) creates the persistent `records` subdirectory owned by uid/gid 50 on every boot, and the agent document has `dependsOn.containers: [{name: records-init, condition: succeeded}]` (#14795); initialization never resets existing records. That subdirectory holds the agent's sessions, ownership (expected hashes of its documents), suspension, and operation records (reserved, accepted, started, completed, uncertain). Files are written to a temporary name, synced, renamed and the directory synced. Missing, corrupt or unwritable records block every change. The leader keeps the journal of multi-step operations (id, immutable inputs, states) in config-key under its incarnation. Before a mutating bridge call is submitted, its dispatch intent is persisted. A new leader first has every reachable agent durably close the previous incarnation's sessions under the same lock that admits work, so nothing more is dispatched under them; it then imports every unresolved reservation (reserved, accepted, started, uncertain), including dispatched bridge calls. Such a call keeps its reservation until its completion is seen and its effect reconciled, or its execution is proven impossible; an effect that is merely not visible yet proves nothing, and lost completion evidence leaves the operation uncertain and conflicting work blocked. An unreachable agent keeps its reservations; expiry releases nothing.
7. **Agents apply their own node.** The agent becomes the only writer of its node's Ceph documents: it applies a granted revision with `ApplyConfiguration` through its socket (`machinedAccess`, requesting `os:admin`), keeps every document it does not own, and records the expected hash of every document it owns. If an owned document is changed or missing, or a Ceph document appears that it did not write, it stops applying and reports drift. Talos has no conditional apply, so this rule is operational, as plan 01 recorded. Without mons no new grant is admitted; work whose confirmation was already obtained finishes or is recorded as uncertain.
8. **Exec, jobs and OSD identity.**
   - **Exec** (#14781). A command that a running daemon container can run executes through `ContainerExec` in that container: no document, no config apply, output and exit code from the call. Secrets go over stdin, never as literal command arguments, as Talos audits the argument list and arguments are visible in `/proc` inside the container; the CLI's wrapper then exports the admin key into the executed command's `CEPH_ARGS` environment, readable to root in that container and on that node while it runs. Every exec has a deadline. The agent's execs are read-only and on an allowlist (admin socket queries such as `status` and `perf dump` with an explicit socket path, `ceph --admin-daemon /var/run/ceph/ceph-<entity>.asok ...` (Ceph's default socket in the daemon's own container), which skips the name lookup through `ceph-conf` and starts no other program); everything that changes the node or the cluster goes through a job, an apply or the bridge, so no reservation ever depends on an exec and suspension (item 11) has no execs to reconcile. A background process an exec leaves behind can outlive the call (Talos ends the session, not its descendants), which is one more reason the allowlist holds only commands that do not fork. The CLI's execs (item 11) are covered by the request uuid protocol.
   - **Jobs** (#14795) stay for work that needs a container of its own: OSD provisioning, zap, offline repair and recovery. A job document has `restart: {policy: never}` and exits; its outcome is the `completed` or `failed` state with exit code and error, and its payload (OSD id and uuid, output) is a result file. The parking entrypoint and the log markers go away.
   - **Records.** Talos runs a `never` container again after every reboot (per boot by design, smira on #14733), so the record protocol stays: a job claims its id atomically in `jobs/<fsid>/<id>` before it starts, writes and syncs a started record, runs, and writes its result the same way; a claimed id with different inputs is refused. A job document that survives a reboot finds its result and does not run again; one that finds only its started record reports "uncertain" and does not run again. The agent reads results for the leader and deletes a result only after the job document and instance are gone and the leader has durably acknowledged the outcome; a replay tombstone stays.
   - **OSD identity.** OSD provisioning and zap are bound to the disk's stable identity (serial or WWID from Talos) and the cluster fsid, revalidated right before the destructive step; when the OSD redesign moves OSDs onto `RawVolumeConfig` partitions (milestone 5), the identity becomes the volume and its partition. Ceph v20.2.4's `raw prepare` has no `--osd-fsid` and chooses the OSD uuid itself (plan 01), and its `safe_prepare` may roll back with `purge-new` on errors. So before prepare the deployment id, fsid and disk identity are persisted under an exclusive reservation; the uuid is adopted only after the device label and the deployment record agree; an ambiguous label or registration, or a possible rollback, freezes the operation for reconciliation and never repeats prepare or purge automatically. Talos sends SIGTERM to every process in the container, not only to PID 1, so the prepare job sets SIGTERM to ignored before it starts `ceph-volume` (an ignored signal is inherited by `ceph-volume` and the tools it runs) and has `stopTimeout: 4m`: a reboot during prepare then waits up to 4 minutes and ends it only with the SIGKILL. The prepare job, the OSD daemon and zap address the disk by its `/dev/disk/by-id` link carrying the serial, and the job checks the serial right before and after `prepare`; `ceph-volume` resolves the link to the kernel name internally, so a disk swapped within the seconds of `prepare` is detected only afterwards, not prevented. The OSD redesign on Talos raw volume devices (milestone 5) removes that window. Destructive steps stay idempotent on the workload side (smira on #14733): the records prevent replay, they do not make anything exactly once.
9. **`ceph orch` commands**, implementing the exact Ceph v20.2.4 signatures and result types; only mutations record an operation, and unsupported argument values are rejected before acceptance:

   | PoC command | `ceph orch` | Method |
   |---|---|---|
   | `host add`, `host rm` | `host add` (an enrolled node, item 11), `host rm` | `add_host`, `remove_host` |
   | `deploy mon`, `mgr`, `rgw` | `daemon add`; RGW with its own certificate via `daemon add -i` | `add_daemon` |
   | `deploy osd` | `daemon add osd HOST:DEVICE` | `create_osds` |
   | `deploy vip` | `apply -i` with an ingress spec (the one exception to deferred specs, below) | `apply_ingress` |
   | `restart`, `redeploy` | `daemon restart`, `daemon redeploy` | `daemon_action` |
   | `rm`, `rm --zap` of an OSD | `daemon rm`, `osd rm --zap`, `osd rm status` | `remove_daemons`, `remove_osds`, `remove_osds_status` |
   | `upgrade` | `upgrade start`, `pause`, `resume`, `stop`, `status` (an `UpgradeStatusSpec`, not an operation) | `upgrade_*` |
   | `host maintenance enter`, `exit` | `host maintenance enter`, `exit` | `enter_host_maintenance`, `exit_host_maintenance` |
   | `host reboot` | `hardware powercycle HOST --yes-i-really-mean-it`: maintenance enter, Talos reboot, exit, as one operation | `hardware_powercycle(hostname, yes_i_really_mean_it)` |

   Supported arguments; everything else is rejected before acceptance:

   | Method | Supported | Rejected |
   |---|---|---|
   | `add_host` | hostname, addr of an enrolled node, labels | maintenance status on add |
   | `remove_host` | `force` for a host without daemons | `offline`, `rm_crush_entry` |
   | `add_daemon` | one mon, mgr or rgw daemon with host placement; rgw with its own certificate | count, label or pattern placement |
   | `create_osds` | one `HOST:DEVICE` per call | drive group filters, DB/WAL devices, encryption |
   | `apply_ingress` | service id, `backend_service` (Ceph's validation requires it), `keepalive_only: true`, one `virtual_ip`, explicit hosts | haproxy, other placement |
   | `daemon_action` | restart, redeploy | start, stop, reconfig, rotate-key |
   | `remove_daemons` | named daemons | |
   | `remove_osds` | `zap`, `force` | `replace`, `no_destroy` |
   | `upgrade_start` | image | version, daemon types, hosts, services and limit filters |
   | `enter_host_maintenance` | `force` (like the PoC's `--force`) | `yes_i_really_mean_it` |
   | `hardware_powercycle` | `yes_i_really_mean_it` | |

   The module overrides `apply(specs, no_overwrite, continue_on_error)` as the dispatch boundary: Ceph's `apply` does not pass these flags on to `apply_ingress`, so unsupported non-default flags are rejected there before dispatch, and only the `HostSpec` route that `orch host add` uses and the ingress subset are accepted; other service types and previews are rejected before acceptance.

   `daemon restart` uses the Talos `Restart` call on the current instance (`<document>-<generation>`, which the agent reads from `ContainerInstanceStatus` first, as `Restart` does not accept the container name), which since #14788 sends SIGTERM and kills after the daemon's `stopTimeout`; Talos then starts it again under its restart policy. Mutations return once the operation is durably accepted. Every operation has a status by operation id in the journal, shown by a module command (`orch talos operation <id>`, read-only), so a failed host add or removal is visible even without a daemon row; `orch ps`, `osd rm status` and `upgrade status` report progress as in cephadm. Flags Ceph does not pass to the backend (`daemon rm --force`) are not promised.
10. **Control-plane safety.** Disruptive operations (maintenance, reboot, upgrade, removal) are serialized and run their safety checks (`ok-to-stop`, quorum, active+clean where the PoC already checks it) right before each step. An operation that would stop the active mgr first fails over to another mgr (`mgr fail`) and continues under the new leader from the journal; if there is no other mgr it is refused. Upgrade progress, pause and stop are journal state and survive a failover. A quorum-loss freeze stops new grants; already confirmed work is not interrupted.
11. **CLI roles and handoff.** Bootstrap stays a CLI workflow: the CLI deploys the first mon, mgr and the agents as today, imports the initial keys, writes the initial state into config-key, enables the module, then hands each node to its agent: the agent stays frozen until it acknowledges the revision it found on the node, and from then on owns it. Enrolling a new node is a CLI workflow too (until plan 04): the CLI provisions the volumes, certificates and agent on the unowned node, hands it over, and `orch host add` registers it. The CLI's other mutating commands, and `shell`, run `ceph` and `ceph orch` through `ContainerExec` in a mgr container of the cluster (any host with a running mgr; the CLI tries the next one if a host is down), with the `client.admin` key sent over stdin: every command, single or scripted, runs as `bash -c 'IFS= read -r key; export CEPH_ARGS="-n client.admin --key $key"; unset key; exec "$@"' <name> <command...>` with the key on stdin, so the key is in that exec's environment (readable in `/proc/<pid>/environ` by root and the same uid). It is in no file, not in the audited arguments and not in any process's arguments (`ceph` cannot read a keyring from a pipe, spike step 0). The `ceph orch` call goes through a wrapper that carries the CLI's request uuid and the hash of its inputs to the backend; the leader persists the request uuid to operation id mapping in the journal before it answers. A retry through any mgr returns the same operation, a retry with different inputs is rejected, and the mapping survives a takeover. The CLI no longer patches nodes, renews certificates or publishes anything, and no admin keyring is written into a machine config. The agents' operator API remains for suspension and recovery only. Recovery without mons and `rm-cluster` are explicit CLI workflows: the CLI suspends the agents. An agent acknowledges a suspension only after admission is closed and nothing it started is still running (jobs included); recorded uncertain operations keep their reservations and block conflicting CLI work. For an agent that does not answer, the CLI removes its document, verifies every instance has exited, stops or reconciles surviving jobs, and writes the suspension to the node's records through a recovery job. During recovery the CLI keeps its own durable local journal for the jobs it runs and does not depend on a leader; with no mgr running, `shell` execs into a mon container instead. Recovery reads surviving node documents and keyrings, never mon auth or a local inventory, and fails on a missing credential. Resuming needs a new handoff.
12. **Daemon documents** (#14795, #14788).
    - Restart policy: daemons keep the default `always` with `delay: 5s, maxDelay: 2m`, so a crash loop (an OSD started before the mons have quorum after a power cycle) backs off in Talos instead of in the entrypoint's 30s EXIT trap, which goes away. `restartCount` is in `ContainerStatus`, the backoff step in `ContainerRunStatus`.
    - Stop timeout: unset (Talos's 10s) for mon, mgr, OSD and keepalived. RGW is rendered with `--rgw_graceful_stop=true` (off by default in v20.2.4, where Beast then closes connections at once) and gets `stopTimeout` of `rgw_exit_timeout_secs` plus 10s, 130s with the default 120s; this is our choice for draining, not a cephadm value. cephadm's per-service `termination_grace_period_seconds` (the container stop timeout) maps onto `stopTimeout` in milestone 5. Values above Talos's 4m cap are rejected when the daemon is added.
    - Order: a keepalived document has `dependsOn.containers: [<its host's rgw>]`, so on reboot, shutdown and upgrade the VIP moves to the peer before the RGW starts draining (tested with radosgw, `rgw_graceful_stop` set through `ceph config`: an in-flight upload straight to the rebooting node's RGW completed, no failed request through the VIP). Talos does not order removals or replacements in one apply, so maintenance enter, removal and certificate rotation keep moving the VIP first themselves. The order is node-local; nothing orders daemons across nodes.
    - Status: plan 02's mapping learns the new states: `completed` maps to `stopped`, `failed` to `error`; the agent status schema goes to version 2 and carries exit code and restart count.

13. **Admission policy in the agent.** Before applying a granted revision, the agent checks every document; anything not explicitly allowed is refused (fail-closed), reported, and the revision is not applied. Rules per Talos document type:
    - `ContainerConfig`: the name must match a known workload kind under the cluster's fsid prefix (mon, mgr, OSD, RGW, keepalived, the image probe that reads a candidate image's Ceph version before an upgrade, OSD prepare and zap jobs). Each kind has a template compiled into the agent, from the same release as the leader: entrypoint and arguments (the kind's script), security profile and capabilities, `runAs`, network mode, restart policy, stop timeout, the exact set of mounts (source, destination, options: for example `/etc/ceph` read-only for every daemon, `/etc/ceph/mgr/cephadm` for mgrs, `/dev` (writable, as `ceph-volume` changes device ownership) and `/run/udev` read-only for OSDs and their jobs, the cluster's volumes) and the allowed environment variable names. Only the template's parameters may vary, and each has a type the agent checks before anything else: daemon ids match `[a-z0-9][a-z0-9-]{0,62}` and the id in the document name; addresses parse as an IP address (and port); the image is a digest reference from the repositories set at handoff; keyrings parse as a CephX keyring holding exactly the entity the kind and id require (a joining mon gets only `mon.` and runs `ceph-mon --mkfs` with `ceph.conf` (its `mon_host`) and that keyring, as cephadm does, instead of fetching the monmap with `client.admin`; so no mon document carries `client.admin`; the bootstrap mon's first document is written by the CLI and replaced by the plain template after bootstrap); TLS identity certificates and keys (agent, mgr) parse as PEM issued by the agent CA, while an RGW serving certificate is any PEM certificate with its matching key, from the cluster's RGW CA or the user's own; the device of an OSD or job is a disk this node's Talos reports, by its stable identity; `dependsOn` entries name documents of the same cluster on this node. A value that fails its type is refused, so no parameter can carry configuration, commands or path components into a script. The scripts quote every parameter as well. The agent's own document and its `records-init` are not kinds a grant can carry: they stay the CLI's (item 11).
    - `EtcFileConfig`: only the cluster's files, with fixed modes and checked contents: `ceph/ceph.conf` must equal the agent's own rendering from the fsid and the mon addresses (typed as above), so no other option can be set; the module files under `ceph/mgr/cephadm/` must be byte-identical to the copies compiled into the agent, from the same release; the mgr's TLS files under `ceph/talos/` must parse as PEM of the agent CA.
    - `UserVolumeConfig`: only the cluster's volumes (`ceph`, `cephadm-talos`) with their fixed definitions.
    - Any other document type is refused.

    The policy's inputs (the fsid, the allowed image repositories) and the agent's own document come from the CLI at handoff; no grant can change them (agent self-upgrade in plan 04 revisits this). The policy bounds what a leader can run: no arbitrary command, image, mount, privilege, configuration option or module code. It does not stop a leader from removing daemons, granting a zap of a disk the cluster knows, or deploying a Ceph daemon with chosen parameters.

## Spike results (step 0, 2026-10-30)

On the combined Talos build `v1.15.0-alpha.2-51-g8ee5a247e` (`cephadm-talos/combined`), Ceph v20.2.4, QEMU nodes with workload isolation off for the agent cases; spike code in `hack/spike03/`, `cmd/cephadm-talos/spike03.go` and `internal/mgrmodule/talos/spike03.py`, removed in step 1.

- **Module listener and bridge calls.** The module, in the active mgr, serves port 4722 from its own threads. `send_command` from a request thread answers `health`, `osd tree` and a fresh `mgr dump` in about 1ms; the fresh `active_gid` matched the cached map. With the mon restarting, a 2s deadline returned "outcome unknown" at 2.0s, and the late completion arrived about 6s later and was kept (`CommandResult.ev.wait(timeout)`).
- **Agent identity on its own socket.** A container with `machinedAccess`, uid 50, `restricted`: with `os:reader`, both `ApplyConfiguration` (it cannot even read the machine config) and `ContainerExec` are refused with `PermissionDenied`; with `os:admin`, applying an `EtcFileConfig` took 21ms and kept every other document, and exec in the mon container listed its admin socket and ran `ceph --admin-daemon <asok> version` (75ms).
- **CLI exec with the admin key.** `ContainerExec` in the mgr container from the workstation takes about 300ms for `ceph health`. Stdin reaches the command only when it is sent (`talosctl container exec -i`, `ContainerStreamOptions.Stdin`). `ceph -k /dev/stdin` fails (`RADOS permission denied`: keyring loading reads the file's size, zero for a pipe); `ceph -n client.admin --keyfile -` reads the raw key from stdin and works (284ms); the implementation uses a wrapper that exports the key from stdin into `CEPH_ARGS` instead, the same for single commands and scripts (item 11). Talos's audit line and the audit log carry the command line without the key.
- **`records-init`.** `restricted` with CHOWN and FOWNER creates the `records` directory as 50:50, mode 0700, on every boot; CHOWN alone fails at `chmod` once the directory belongs to uid 50. A uid-50 writer depending on it with `condition: succeeded` writes, syncs and renames records, which survive a reboot.
- **`never` jobs.** A job that succeeds ends `completed`; one that exits 3 ends `failed` with `exitCode: 3` and an error carrying its last log line. The succeeding job claims its id, writes a started record and renames its result into place; after a reboot it runs again, finds its claim and does not repeat its work.

### Step 6b, part 3: requests and their authorization (implementation design, 2026-11-01)

The signed-off design leaves open where the module records what it accepted and how that binds key release; this is how part 3 does it. Part 3 comes in two slices.

- Slice A: the ledger and acceptance, key release bound to operations, `daemon restart` and `daemon redeploy`, `orch talos operation <id>`.
- Slice B: `daemon add mon` and `daemon add mgr` with module-issued mgr certificates, `daemon rm` of a mgr that is neither active nor the last, `host rm` of a host without daemons, the leader publishing the module's inventory.
- Later: `host add` with enrollment (step 7); OSDs (6c); mon removal, maintenance, powercycle and upgrade, with control-plane safety (6d); RGW and ingress (6e); the CLI's request uuid wrapper (step 7).

What it protects against: a leader that is wrong or stale, or an agent process that only has the bridge. It does not protect against root on a mgr host: the mgr's CephX key (`profile mgr`) reads and writes every config-key entry and mon auth directly (see `docs/architecture.md`).

1. **Acceptance and the ledger (A).** The module checks the call against the supported arguments (item 9), against the fold (item 3) and against the operations not done yet (from the leader's journal: a lying leader can only make the module refuse commands), and refuses it without a captured incarnation or when a fresh `mgr dump` no longer shows that incarnation active. Acceptance is one ledger entry `cephadm-talos/ledger/<epoch>-<seq>-<id>` written with `config-key set` through the module's own command pool, which reports the mons' result (`set_store` does not). The entry holds the whole canonical operation (version, id, kind, target daemon or host, entity, arguments, optional request uuid, the accepting gid and epoch) and is never overwritten. The module appends one entry at a time, with sequence numbers without gaps. When an append's outcome is unknown, the caller is told the operation may exist, and the module writes the same key with the same content again until the mons answer, before it accepts anything else; a key that reads back as absent proves nothing, as the first write may still land. The ledger is outside `mgr/`: the bridge's store calls cannot reach it, the mgr does not cache or log it, and it holds no secret.
2. **One executable prefix for every reader (A).** Right after capture, before accepting anything, a module writes a takeover entry `<epoch>-0-takeover` with, for every incarnation whose entries it finds since the previous takeover entry, the highest sequence number it found. Readers walk the incarnations in epoch order. An entry, takeover entries included, is valid only if its sequence number is at most the cutoff that the first later valid takeover entry records for its incarnation (-1 if that entry does not name it, so even its takeover entry is void), or if there is no later valid takeover entry. A void takeover entry sets no cutoffs. So a stale module's append, or a superseded module's delayed takeover entry, that lands after a successor's valid takeover entry is void for every reader; an append that landed before it was accepted in good faith and runs; and the takeover entry stays small.
3. **The fold (A).** The authorized daemons and hosts are those of the CLI's sealed state (the module reads the `cli` manifest's records itself and requires `sealed`; no incarnation can write `cli` through the bridge), with the executable ledger entries applied in order: an add counts from acceptance and opens a new generation of the daemon (identified by the add's operation id), a removal counts from its retirement (items 4 and 8), so a removal accepted later does not break an earlier operation that still renders the daemon.
4. **Key and secret release (A).** Every credential call first checks with a fresh `mgr dump` that the incarnation is active, then the fold. `auth get`: `mon.` while the fold has a mon, `mgr.<id>` and `client.rgw.<id>` for those daemons; `osd.<n>` is not needed (an OSD's key is on its disk) and `client.bootstrap-osd` waits for 6c. `secret get`: a host's mgr keys while the fold has a mgr there, `rgw/server.key` while it has an RGW, `rgw/vrrp` while it has a VIP. This replaces the inventory check, as the leader publishes the inventory itself. In slice B: `auth get-or-create` and `mgr cert` only for the add that opened the daemon's current generation, while that generation is open. A removal goes in three module steps, each an entry or a command whose result the module knows: it closes the generation (an entry; from then on no `get-or-create`, `mgr cert` or secret write for it is accepted), waits until every mutation it sent for that generation has a definitive result (a timed-out command may still be resent and run, so a timeout keeps the removal pending), then runs `auth rm` and deletes the generation's issued TLS keys, and writes the retirement entry, which takes the daemon out of the fold. A later add opens a new generation; nothing of an older one is released again. A mutation sent by an earlier mgr process cannot be fenced this way (the mons have no conditional auth change); this is accepted like the non-atomic leadership check.
5. **Execution and its checkpoint (A).** The leader reads the ledger through a read-only bridge call every tick and carries out the executable operations strictly one at a time in ledger order. After each one, it publishes its state with the ledger key of that operation as the last applied one; a successor takes this checkpoint with its baseline and starts after it. Progress within an operation (phase, hosts done) goes into the journal. An operation that cannot finish (an agent unreachable for 10 minutes) ends as failed and the next one runs. An operation interrupted by a takeover after its effect but before the checkpoint runs again; its grant carries the operation id, so an agent that still has the operation's record refuses to run it twice. The journal's request records (`req/<id>`) stay for the leader's own `revision` requests, which use the fold of the whole ledger.
6. **Restart and redeploy in the agent (A).** A document whose rendering did not change is not granted again, and applying an identical document restarts nothing, so a grant may carry an action, `restart` of one document. The inputs hash covers the action, the document's kind, name and owned hash; the confirmation signs it as for documents. Admission: the document is a daemon `ContainerConfig` of this cluster that the agent owns on its node, unchanged (not a job, probe, the agent or records-init). The agent resolves the current instance from `ContainerInstanceSpec`, records it in the operation record before calling Talos `Restart`, and a lost answer leaves the operation uncertain instead of retrying it. `redeploy` is a revision of the daemon's host followed by the restart, recorded as two phases. Both run under the same lock, fence, suspension and confirmation-expiry checks as a grant of documents.
7. **Mgr certificates from the module (B).** A bridge call `mgr cert` naming an executable `daemon add mgr` whose daemon is in the fold. The module reads the agent CA key with a mon command, issues the server certificate (the host's address and name from the fold) and the client certificate (3 years, the `mgr/<host>` identity), writes both keys as secrets under a fresh attempt id, `issued/<op>/<attempt>/server.key` and `client.key`, and returns the certificates with the attempt id. The leader puts the certificates and the attempt id into the host's state, and rendering reads the keys of that attempt, so a certificate and its key always come from the same attempt, also after a retry or a late write. `secret get` releases an attempt's keys only while the generation of `<op>` is the mgr's current, open one. Renewal stays plan 04.
8. **State changes by the leader (B).** The leader changes its cluster state with the `state` package and publishes all four records (`cluster`, `hosts`, `daemons`, and `inventory` rendered as the CLI does). Then it grants the affected hosts their revision (a mon changes `ceph.conf` on every host), recording each host in the journal. A removal grants the removal of the daemon's documents, waits until its instance is gone, then asks the module for the bound `auth rm`. A host leaves the state only after its daemons and documents are gone; then the leader asks the module to retire it, and the module writes the host's retirement entry once the fold has no daemon on that host. Its agent keys stay in the secrets until `rm-cluster`, as the leader cannot write secrets. The leader checks again right before removing a mgr that it is not the active one.
9. **Ceph's methods.** `remove_host(host, force, offline, rm_crush_entry)`, `add_daemon(spec)` returning a list with the operation id, `remove_daemons(names)` returning a list (each name its own operation, all checked before any is accepted), `daemon_action(action, daemon_name, image, force)` with `restart` and `redeploy` (`redeploy` has its own CLI handler; `image` and `force` are rejected). `daemon add mgr` passes a `ServiceSpec` with placement: exactly one host, no `count_per_host`, network or explicit daemon name, as mgr ids are host names.

### Step 6c: OSDs and approvals (implementation design, 2026-11-01)

Step 6c carries out OSD creation and removal through the leader, with the part of ROADMAP milestone 4's admission item that belongs to it (approvals of images and disks, zap of known disks, mgr key pairs; the RGW certificate checks wait for 6e). Slices: A, approvals and their admission; B, jobs through the agent and `ceph orch daemon add osd`; C, `ceph orch osd rm` with `--zap` and `osd rm status`. Out of scope: the OSD redesign on raw volume devices (milestone 5), DB/WAL devices, encryption, drive group filters, upgrade (6d), `host add` (step 7).

What it protects against: a compromised leader, mgr or mgr host can no longer get an agent to admit a new document with an image, or a preparation or zap job on a disk, that the operator did not approve, nor a zap of a disk without an OSD label of this cluster unless the operator approved that zap. Limits: rollback protection is per agent, not a cluster-wide freshness guarantee (item 3); approvals bound what is newly admitted, not what already runs (a withdrawn image keeps running and restarting until its document is replaced); a node's own compromised agent or root, and an agent on a control-plane node that reaches other nodes with the Talos CA (see `docs/architecture.md`), are not bounded; the shared `client.bootstrap-osd` key, once released, can register OSDs (item 7).

1. **The approval authority (A).** At bootstrap the CLI creates an Ed25519 approval key. The private key stays in the workstation's local state only (not in config-key, the secrets or any node's config) and nothing renews it (plan 04). The public key goes into every agent's document, which is the CLI's (a handoff document no grant can change, `node.go`); an agent without it admits no image and no job. The operator certificate does not qualify: the agent CA's key is a secret the mgr can read.
2. **Approvals (A).** An approval is a signed record: version, fsid, serial, the image digests the cluster may run, and disk entries `{host, serial, action (prepare or zap), since}`, where `since` is the serial of the approval that first listed the entry. The workstation is the authority over the history: its local state keeps the last approval it signed (serial, content and hash), written with fsync before it is published. `cephadm-talos approve` (allowed after the handoff) builds the next approval from that local copy, not from config-key: images to add or drop, disk entries to add (a new entry, `since` = the new serial) or drop; other entries carry over unchanged. It never signs two contents under one serial: an approval whose publication had no answer is published again unchanged. It publishes with `client.admin` through exec to `cephadm-talos/approvals/<serial>`, outside `mgr/`. The handoff signs and publishes serial 1, the cluster's Ceph and keepalived digests and no disks, before it seals.
3. **Approvals travel with grants (A).** The leader reads the newest approval through a read-only bridge call `approval` (the module reads it with a mon command) and attaches it to every grant. The agent verifies the signature against its pinned key and the fsid, refuses a serial below the highest it recorded, and records a higher one. Admission uses the highest recorded approval. Rollback protection is per agent: a leader can hold a newer approval back from an agent, which keeps that agent at what it has, including entries a newer approval dropped. The agent's highest approval and its consumed disk entries are never pruned; once handed over, an agent without them admits no job.
4. **Admission (A).** Every granted `ContainerConfig` runs an image digest of the agent's approval, besides the repository check. An OSD preparation job needs a disk entry `prepare` for its disk's serial on this host; a zap job one `zap`, or else its label check (item 5). The agent validates the whole grant first, then reserves each disk entry it uses durably for that job (job id and inputs) before anything is applied; a reserved entry admits only that job (its retries included) and no other; two jobs of one grant cannot use the same entry. A failed or abandoned job keeps its entry consumed: a new approval of the disk is a new entry. `JOB_INPUTS` is computed by the agent from the validated parameters (and the entry or the label check used), not taken from the grant. OSD daemon documents are not gated by disk entries: activation destroys nothing. The mgr's key and certificate are checked as pairs on the documents the node will hold after the grant, for both the client and the server pair, whichever half changes.
5. **Zap and the label (A, C).** The zap job's script reads the device's BlueStore label (`ceph-bluestore-tool show-label --dev <by-id link>`), and requires it to succeed with valid JSON and a `ceph_fsid` equal to the cluster's; a zap of an OSD's removal also requires the label's `osd_uuid` to be that OSD's. A missing, corrupt or foreign label needs a `zap` disk entry, whose flag skips only the label requirement, never the serial check. The disk check, label read and wipe are separate steps: a disk swapped within them is not prevented, as today (the raw volume redesign in milestone 5 removes this).
6. **Jobs through the agent (B).** A grant can carry a job document; its operation record names the job id and expected inputs before anything is applied. The operation stays started until the container ended and the job's result file (on the agent's records volume, readable by the agent: the jobs directory is 1777 and results 0644) is read into the record, bounded (the job writes at most 16 KiB of output; the record keeps the structured fields: rc and, for a preparation, the OSD id and uuid). Outcomes: completed with rc 0; failed with the rc; refused (no result, inputs differ); uncertain (started record without result: the job never repeats it, the operation freezes for the operator). An unresolved job blocks other jobs on that node, not document grants. A job's operation record and result are kept, exempt from pruning, until the leader acknowledges them: it stores the result in its journal, then sends a grant that removes the job document and carries an acknowledgement naming the job id, its inputs hash and the recorded rc, which the agent checks against its record. A grant that removes a job document with an unacknowledged result and no matching acknowledgement is refused. After the acknowledgement the agent writes a permanent tombstone for the job id, deletes the result once the document and instance are gone, and refuses that job id again; the job script refuses to run under a tombstone too. Job ids come from the operation and its phase (16 hex digits), never at random.
7. **Ledger and fold (B, C).** New operation kinds `create_osd {host, device}` (the module accepts an exact host of the fold and a `/dev/` path) and `remove_osd {daemon osd.<id>, host, uuid, zap, force}` (the uuid from the fold). Before the preparation, the leader asks the module to bind the creation to its disk: the module writes a `bind` entry once per creation, with the disk's serial and by-id link (from the node report) and the preparation job's id, and refuses a second, different one; confirmation and `client.bootstrap-osd` follow that entry. The fold keeps an OSD's id and uuid: the CLI's from the sealed inventory (which gains the OSD uuid), the leader's from a module `confirm` entry. The leader asks for the confirmation after the creation; the module writes it only when the OSD map has that id with that uuid up, no OSD of the fold has that id, and `osd metadata <id>` names the operation's host and a `device_ids` identifier that is the bound serial or contains it as `_`-separated parts (spaces as `_`; Ceph builds the identifier from udev's vendor, model and serial, or uses `ID_SERIAL` as is). Missing or different metadata keeps the operation pending until it fails after 10 minutes; a disk whose Ceph identifier does not contain its serial cannot be confirmed, and its OSD stays outside the fold (removable only with the CLI's `shell`). This is corroboration, not proof: a holder of `client.bootstrap-osd` can register an OSD with chosen metadata. The leader asks the module to close a creation that failed (a `close` entry). `auth get client.bootstrap-osd` names its creation and is released only while that creation is executable, bound, neither confirmed nor closed. For a removal, the module answers three calls bound to an executable removal of that id and uuid, checking both against the OSD map first: `osd out`; `drain`, which unless the removal has `force` succeeds only when `osd safe-to-destroy` (JSON; `safe_to_destroy` must list the id, the return code is 0 either way) agrees while the OSD still runs, and then writes a `drained` entry; and the retirement, which needs that entry, waits until the OSD map shows the OSD down with that uuid (it issues no `osd down`), checks `safe-to-destroy` again unless `force`, and runs `osd purge-actual` of that id. A retirement that finds the id gone from the OSD map, with no purge it sent still unanswered, finishes (an earlier purge landed, as Ceph treats a purge of an absent id as done); one that finds the id with another uuid mutates nothing and fails.
8. **Leader flows (B, C).** Creation: the disk's serial and `/dev/disk/by-id` link from the node report; the deployment (deploy id, serial, link) published in the state before the job; the preparation job; the OSD id and uuid from its result published; one revision with the OSD daemon and the job's acknowledgement; the module's confirmation, or its closure on failure. Removal: `osd out`; the module's `drain` (the OSD keeps running until it agrees, unless `force`); the OSD marked in the state as leaving (not rendered, document removed by the revision) with its id, uuid, serial and link kept; its instance gone; the module's retirement (down, safety check again, purge); with `--zap`, the zap job (label and uuid check) and its acknowledgement; only then the OSD leaves the state. A host with a leaving OSD is not removed. Each step is recorded in the journal and resumes after a takeover.
9. **Ceph's methods (B, C).** `create_osds(drive_group, skip_validation)`: `daemon add osd HOST:DEVICE` sends a placement `host_pattern` of HOST, which must be an exact host of the fold (no pattern); `data_devices.paths` one `Device` whose `.path` is a `/dev/` path and has no other attributes; every other drive group field at its default; `skip_validation` false. `remove_osds(osd_ids, replace, replace_block, replace_db, replace_wal, force, zap, no_destroy)` with `force` and `zap` only, each id its own operation, all checked before any is accepted. `remove_osds_status()` returns, per removal not finished, `osd_id`, `hostname`, `drain_status` (the phase), `pg_count`, `replace` (false), `force`, `zap` and `drain_started_at`. Creation and removal return strings.

The live check of slice C chooses an OSD that `safe-to-destroy` can agree to (PG placement and free space on the others), or uses `--force`, and says which.
